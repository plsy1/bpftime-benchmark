## Findings (most severe first)

### 1. BPF_NOEXIST on an existing key takes a value slot: pool lock on every such call, and E2BIG where the kernel says EEXIST once the spare slots are held by in-flight inserts
- Severity: medium (documentation claims a guarantee the code does not give; a kernel-visible error code difference under a full map with contention; a regression against the code a73f6753 replaced).
- Commits: a73f6753 (code), e1677f0d (CLAUDE.md claim).
- Files at 94f9ba8f: `runtime/src/bpf_map/userspace/per_cpu_hash_map.cpp:133-147` (`update_with`: for `base_flags == BPF_NOEXIST` the `with_existing_value` branch is skipped and `acquire_slot` runs at line 145 before `table.update(..., no_exist)` at 149; the slot is released only at 153); claims at `runtime/src/bpf_map/userspace/per_cpu_hash_map.hpp:27-29` ("The pool's free list has a spinlock, taken only to insert a new key or to delete one; lookups and updates of an existing key never take it") and `CLAUDE.md:1273-1274` ("`pool_lock` ... taken only to insert a new key or to delete one").
- What is wrong: the pre-a73f6753 code returned EEXIST for NOEXIST-on-existing before touching the slot pool (`if (base_flags == BPF_NOEXIST && existing_value != nullptr) ... EEXIST` preceded `acquire_uint32_value`); a73f6753 dropped that check. Now every NOEXIST update of an existing key (program path `elem_update` and bpf() path `elem_update_userspace`) takes the pool lock, memsets `value_size * ncpu` bytes, takes the stripe lock, and takes the pool lock again to give the slot back. So the single global `pool_lock` (the thing a73f6753 set out to remove from the hot paths) is back on a path that BCC-style `lookup_or_try_init` (lookup miss -> update NOEXIST) hits on every lost race, and the pool is only `max_entries + ncpu` slots.
- Failure scenario: table full (max_entries keys present, free slots = ncpu = 6 here); more than ncpu threads are simultaneously between `acquire_slot` and the stripe lock with NOEXIST updates of keys that exist (e.g. all racing on the same hot key after a lookup miss, or stalled on a stripe a tool's `get_next_key` walk is locking); the next NOEXIST update of an existing key gets E2BIG. The kernel's `htab_percpu_map_update_elem` finds `l_old` under the bucket lock and returns EEXIST without allocating. A program doing `err = update(NOEXIST); if (err && err != -EEXIST) drop; else re-lookup` drops the event.
- Evidence: reproduced. `/tmp/claude-2002/-home-jetson-src/6ac0883f-4479-466c-bec5-5fa31cffe4de/scratchpad/review-20261105/percpu/e1_noexist` (built from `e1_noexist.cpp` with `./build.sh e1_noexist`), `timeout 60 ./e1_noexist`:
  ```
  (a) update(existing key, BPF_NOEXIST) while the pool lock is held: WAITED for the pool lock (ret -1 errno 17 File exists)
  (a) bpf() update(existing key, BPF_NOEXIST) while the pool lock is held: WAITED for the pool lock (ret -1 errno 17 File exists)
  (b) in-flight NOEXIST update of existing k1 (blocked on the stripe lock): ret -1 errno 17 File exists
  (b) meanwhile program update(existing k2, BPF_NOEXIST): ret -1 errno 7 Argument list too long (kernel: EEXIST)
  (b) meanwhile bpf() update(existing k2, BPF_NOEXIST): ret -1 errno 7 Argument list too long (kernel: EEXIST)
  ```
  (b) forces the condition with `ncpu = 1`, 2 entries full, one in-flight insert holding the single spare slot; on this box it needs 7 concurrent in-flight NOEXIST-on-existing calls. The `[percpu-locks]` tests cover only BPF_ANY/BPF_EXIST, so they cannot see this; a NOEXIST-on-existing case would have failed.
- Fix direction: cheap: for NOEXIST, look the key up first (lock-free `table.elem_lookup`, or a tri-state `with_existing_value`) and return EEXIST without a slot, restoring the old common-case behaviour. Structural: take the slot under the stripe lock, as the kernel pops its freelist under the bucket lock (an `update_with(key, mode, make_value)` on the table that calls back under the lock; pool lock nested inside the stripe lock is safe, nothing holds the pool lock while taking a stripe); that also removes the in-flight spurious E2BIG and the leak window of finding 2. Either way fix the two comments.

### 2. A process killed between `acquire_slot` and the table insert loses the slot; after more than ncpu such deaths the map's capacity is below max_entries (not documented for the per-CPU hash)
- Severity: low (one slot per death, kernel holders cannot die; the analogous element loss is documented for the hash map, the per-CPU section only documents the held lock).
- Commits: a73f6753, e1677f0d.
- Files: `per_cpu_hash_map.cpp:144-149` (slot taken at 145, published only by `table.update` at 149, which first waits for the stripe lock); `CLAUDE.md:1282-1283` mentions only the held `pool_lock`.
- Failure scenario: a traced process is killed (SIGKILL, OOM) while one of its threads waits for a stripe lock in `table.update` holding a fresh slot (every NOEXIST-on-existing call is in that window, finding 1). The slot is neither in the table nor on the free list. With k > ncpu such deaths over the life of the shm, inserts fail with E2BIG at `max_entries + ncpu - k` keys.
- Evidence: reproduced. `e3_death_leak` (`timeout 60 ./e3_death_leak`): `insert 62 failed: errno 7 ... ncpu 6, 9 children killed between slot and insert, max_entries 64, inserted 61 (slot capacity 70 - 9 leaked = 61)`.
- Fix direction: take the slot under the stripe lock (the structural fix of finding 1), or document the loss next to the hash map's.

## Checked, no defect found
- Lock-free lookup ordering on aarch64 (both key paths): the slot number is read with an acquire load inside `lookup_read` (after the acquire key load / before the acquire fence and the word re-check), chunk offsets are written once under the pool lock before any slot of the chunk is handed out and reach readers through the insert's release stores; a reused element shows a changed generation, so a lookup cannot pair a new key with an old slot number. Stress: `e2_stress` (4-byte keys, 32M ops in 5 s) and `e2_stress_k8` (8-byte keys, the memcmp path, 25M ops): readers/existing-key updaters of 8 keys present throughout while 64 keys of the same bucket are inserted/deleted/lookup_and_deleted from program and bpf() paths, plus a bpf()-side copier and `get_next_key` walker, through two mappings of the segment at different addresses: 0 wrong values, 0 wrong copies, 0 misses, 0 update failures. That also validates the `this`-relative chunk offsets, the `offset_ptr` manager and the shm vectors across address spaces.
- Slot pool: each path releases its slot exactly once (`exists`, `full`, delete, lookup_and_delete); deletes of one key are serialized by the stripe lock so no double release; the free list is LIFO under one lock, no ABA. Pool and stripe locks are never nested (pool -> segment allocator mutex only), so no deadlock. Capacity: the table (`max_entries` elements) binds; proof that distinct new keys can never get a spurious E2BIG (k in-flight inserts exhaust slots only if the table would be full after them); only lost races and NOEXIST-on-existing can, as in finding 1. Chunks are never freed before the destructor, which deallocates `allocate_aligned` blocks with `deallocate` (supported by Boost).
- Stale value pointer after delete + slot reuse writes into the next key's values: documented in the header and CLAUDE.md, identical to the kernel's preallocated htab (immediate `pcpu_freelist_push`, LIFO).
- CPU index: `sched_getcpu` bounded by the map's fixed `ncpu` (`bpftime_cpu_index_limit`, highest possible + 1) on every program path (lookup ENOENT, update/delete EINVAL); syscall-layout conversions guard `ids[i] < ncpu`; `/sys/devices/system/cpu/possible` is `0-5` here. Buffer sizes match: `percpu_userspace_size` == `get_userspace_value_size` == what the syscall server memcpys; `lookup_and_delete_userspace` writes stride x num_possible bytes, what libbpf allocates; the syscall server passes `from_syscall=true` to lookup/update/delete.
- Torn values between a bpf() copy and program writes: copies are per 8-byte word (aligned), like the kernel's long-wise `copy_map_value_long`; no worse.
- Flags: low 32 bits only (bpftime's high bits masked), `BPF_F_LOCK` EINVAL as the kernel's percpu htab; BPF_ANY/EXIST/ENOENT/E2BIG paths follow the kernel (apart from finding 1); `BPF_F_ZERO_SEED` is `1 << 6` (correct) and the env var is read in the creating process (7670cee5).
- Lookup of a key being updated never misses (existing-key updates write in the slot under the stripe lock, the table element is never replaced for the per-CPU hash, so `replace_locked`/spares are unused).
- Tests: `[percpu-hash],[percpu-locks],[cpu-bounds],[percpu-layout],[slot-pool],[flags]` at `build-jetson-daily` pass (20 cases, 5381 assertions). The `[percpu-locks]` cases do exercise what they claim (pool lock held: ANY/EXIST updates and lookups complete, new key waits; stripe lock: existing-key update waits only for its stripe; handler lock never waited for). "reuses value slots without stale data" really depends on the zeroing (slot 0 is reused LIFO). Gap: no NOEXIST-on-existing case.
- `bpf_map_lookup_percpu_elem` (helper 195) is only an enum, not implemented: pre-existing, outside the range.
- Concerns, not measured (shared machine): all CPUs' values of one key are packed `value_size` apart, so a hot key updated from several CPUs bounces one cache line (the layout predates a73f6753 and was kept; the kernel's percpu areas separate CPUs); `sched_getcpu` is a real system call per operation on aarch64 (no vDSO getcpu); finding 1 makes the NOEXIST-lost-race path pay two pool-lock round trips plus a `value_size * ncpu` memset.
