## Findings (most severe first)

### 1. [high] The hook clears `busy` before it has read its frame back; a handler on an alternate stack that makes a hooked call in that window builds its frame over the live one (the interrupted thread's registers and sp are corrupted: it stalls, or silently continues on the signal stack)
Commit 7d9690c3. W/attach/text_segment_transformer/text_segment_transformer.cpp: `str xzr, [x10, #16]` (busy := 0) at :544; the frame is still read at :546-:577 (`ldp x9, x10, [sp, #240]` ... `ldp x29, x30, [sp, #224]`, `ldr x17, [sp, #776]`) and sp leaves the hook stack only at :581/:590 (`mov sp, x17`). The window is :546-:581 (interrupted pcs syscall_hooker_asm+468..+552 in the experiment binary, 0x17cd4..0x17d28 in the shipped .so: 22 instructions). The comment at :362-364 ("`busy` is set before sp moves onto the hook stack and cleared while sp is still on it, so a handler arriving in between always sees one of those cases"), :536-537 ("the frame stays readable below any handler's") and CLAUDE.md:875-877 consider only handlers that run on the current stack. A handler with SA_ONSTACK runs on the sigaltstack: sp is elsewhere and busy is already 0, so its hooked call takes the switch path (:413-420) and builds its 784-byte frame at hi-784, the frame the interrupted hook is still reading.
Failure scenario: thread T is in a hooked call's epilogue between :546 and :581. A signal with an SA_ONSTACK handler arrives and the handler makes any hooked system call (glibc: e.g. write to a self-pipe; Go: every handler, because Go returns through its own rt_sigreturn svc, which is rewritten and goes through the hook on the direct path). The nested hook writes T's frame. After sigreturn, T restores the handler's x0-x30/NZCV/FPSR from the frame, takes sp from the nested slot (an address on the sigaltstack) and branches to the handler's gate: when only the slot read at :577 was still pending, T silently continues on the signal stack; when register reads were pending, T loops forever through the handler's tail -> rt_sigreturn -> the same corrupted epilogue (the thread hangs while still handling signals; nothing crashes, nothing is logged). Observed landings cluster at :549 (+480, the instruction after `msr fpsr`, a slow serializing write where IPI-delivered signals are taken), so the window is hit far more often than its length suggests. Realistic triggers: any Go program under the transformer (SIGURG preemption, GC stack scans, SIGPROF, SIGCHLD all land on Go's gsignal stack and return through the hook); JVM/OCaml/Rust-style SA_ONSTACK handlers that make a system call.
Evidence: reproduced. S/altstack_race (core library linked statically, pass-through hook doing a little work): `./altstack_race 3 50000000 2000` (SA_ONSTACK handler calling syscall(SYS_getppid); a signaller thread) -> "victim STALLED for 3 s at iteration 487681 ... first hit: at victim iteration 487681" (S/altstack_race5.log run 2: the stall begins at the first signal that found sp on the hook stack with busy == 0, pc +536 = `ldp x29, x30`); run 1: first two hits at +540 moved the victim onto the sigaltstack silently, a later +480 hit stalled it. Controls: mode 2 (handler without an altstack, same call) and mode 1 (altstack, no call) complete 2,000,000 iterations (S/altstack_race.log, altstack_race2.log). End to end with the shipped build and a plain program (no bpftime code linked): `LD_PRELOAD=.../dev-b60b99c3/libbpftime-agent-transformer.so AGENT_SO=/nonexistent ./e2e_plain race 2000` stalled in 2/2 runs (S/e2e_plain.log); the same program without the preload ran its 10 s cap without stalling. The existing test "a handler on an alternate stack leaves the hook's live frame alone" interrupts a blocking call with busy == 1, never the epilogue.
Fix direction: make the liveness marker the top frame's own slot word (bit 0 of [hi-8] while that frame is live; the entry test loads hi once more and reads [hi-8] instead of `busy`) and zero it with `str xzr, [sp, #776]` right after `ldr x17, [sp, #776]`, which is after `ldp x16, x18, [sp, #128]` and the last frame read; nothing is read from the frame after it is released, no scratch register is needed, and "cleared while sp is still on the hook stack" still holds. The CFA expression derefs the slot, so the three instructions between the zero and `mov sp` need their own `.cfi_def_cfa_expression` on x17 (breg17, const1s -16, and, plus_uconst 16).

### 2. [medium; high for Go with programs attached] `busy` is cleared only by the epilogue, so a vfork/posix_spawn/system child's exec or _exit, and a siglongjmp out of a handler, leave it set: every later hooked call of that thread stays on the caller's stack (for Go with programs attached the 18 KB-on-a-goroutine-stack crash the commit fixed comes back after the thread's first os/exec)
Commit 7d9690c3. W/attach/text_segment_transformer/text_segment_transformer.cpp:413-417 (switch only when busy == 0), :538-544 (the only clear), :725-747 (`syscall_hooker_cxx`: execve/exit_group go through the hook with the frame live at the top). A CLONE_VM child without CLONE_SETTLS (glibc posix_spawn/system/popen, Go's os/exec on arm64: clone with CLONE_VFORK|CLONE_VM) shares the parent thread's TLS and hook stack; its hooked execve or exit_group never returns through the epilogue, so the parent's `bpftime_hook_stack.busy` stays 1. A siglongjmp out of a handler that interrupted a hooked blocking call (bash, interpreters) abandons the live frame the same way. Afterwards sp is never on the hook stack and busy is 1: the "stay" branch at :414-415 is taken forever. CLAUDE.md:1118-1123 documents the analogous `in_hook` only for a vfork child *killed* inside the hook; `busy` sticks on the normal exec path, and the three documented "stay" cases (CLAUDE.md:870-875, code :355-361) omit it.
Failure scenario: a Go program with syscount attached calls exec.Command once on thread M; every later hooked call on M runs the 18 KB JIT frame on a goroutine stack (the documented crash: "unknown caller pc", SIGSEGV). glibc programs silently revert to the pre-commit 0.9-1.4 KB (18 KB with programs) below sp.
Evidence: reproduced. S/busy_stuck (`./busy_stuck spawn|system|vfork|longjmp|none`, S/busy_stuck.log): bytes written below the caller's sp by a hooked getpid: 32 before; 1272 after posix_spawn, after system, after vfork+_exit, and after a siglongjmp out of a SIGUSR1 handler interrupting read(); `none` stays 32. Shipped build: `LD_PRELOAD=...dev-b60b99c3/libbpftime-agent-transformer.so AGENT_SO=/nonexistent ./e2e_plain spawn` -> "before 32, after posix_spawn 944" (S/e2e_plain.log).
Fix direction: let the hook recognize a stale marker: a live top frame can exist only while sp is on the hook stack or on the thread's sigaltstack, so record the altstack bounds from hooked `sigaltstack` calls in the TLS block and switch whenever sp is on neither (covers exec, exit and longjmp); or, narrower, issue execve/execveat/exit/exit_group on the direct path after the hook's pre-work (as clone), so the frame is released before the svc.

### 3. [medium] Each thread's hook stack (two VMAs, 192 KiB of address space, at least one resident page) is never reclaimed; a process that churns threads exhausts `vm.max_map_count` (stock 65530: about 32k threads over the process lifetime), after which its own mmap/pthread_create/malloc fail
Commit 7d9690c3. W/attach/text_segment_transformer/text_segment_transformer.cpp:678-710 (`allocate_hook_stack`, "Never given back"), :739. The stack is keyed to the thread's TLS; glibc reuses a dead thread's stack and TCB for a new thread with a fresh zeroed TLS image, so the new thread maps another one and the old one is unreachable. CLAUDE.md:862 says "never unmapped" but not that it is two VMAs and 4-24 KB of RSS per thread ever created, nor that the VMA budget consumed is the application's.
Failure scenario: a thread-per-request server or a program using short-lived std::thread/pthreads, traced for hours: after ~32,700 threads (stock max_map_count) mmap returns ENOMEM for the hook stack (that fallback is fine) and for the application's own thread stacks and malloc arenas: pthread_create -> EAGAIN, allocation failures; RSS grows by >= 4 KB per thread meanwhile.
Evidence: reproduced. S/thread_churn (`./thread_churn 16384 1`, S/thread_churn2.log): 84 -> 32,854 mappings, VmSize 6 MB -> 3.16 GB, VmRSS 4.6 MB -> 70 MB after 16,384 create+join threads (one hooked call each); without the hook 29 -> 31 mappings, 3.4 MB RSS. This machine has max_map_count raised to 1,048,576, so the ENOMEM itself was not provoked; at the stock 65530 the count above crosses it at ~32.7k threads.
Fix direction: keep a process-wide list of hook stacks of exited threads (the clone hook records (tid, stack); a later allocation probes dead tids with tgkill as the perf shards do, or the exiting thread marks its own with a futex/TID word) and reuse or munmap them at the next allocation.

The build's transformer suite (cancel through the hook, cancel in another namespace, backtraces from a handler, Go-style restorer) passes: 49 passed, 1 failed-as-expected (S/transformer_tests.log).
- A handler without an alternate stack interrupting a hooked call runs on the hook stack below the live frame and stays (control mode 2: 2M iterations, 12k signals, no fault); a handler on an altstack while busy == 1 stays on the altstack (the window in finding 1 is the only hole found).
- clone/clone3 with a new stack and TLS: hi == 0, the first call stays and allocates; the direct path releases busy before the svc, so a fork child or a new thread starts with busy == 0; note_clone_syscall unchanged, reads clone_args via the recovered application sp.
- 128 KiB above a 64 KiB PROT_NONE guard holds a signal frame plus the 18 KB JIT frame; overflow faults on the guard. perf dwarf unwinding of a sample taken on the hook stack cannot reach the application's frames (its 8 KB stack copy is of the hook stack): a profiler limitation, not a defect.
- Stack trace map: writer order (count 0, release fence, frames, hash, count release) and reader order (count acquire, hash, frames) mean a false match needs a stored hash equal to the probe's, i.e. the probe is the old or the new trace, so a mix never passes for a third (the test reproduces the commit's claim); both find and fill clip nr to value_size/8 before hashing, so ids agree; a record's offset is relative to its slot (valid at any mapping address), published with release after zero-fill, allocated once under the lock and freed only in the destructor, so a lock-free reader never follows freed memory; delete clears the count under the handler lock; -EFAULT for no frames, -EEXIST on an occupied slot, -ENOMEM on a failed allocation, ids in [0, max_entries) match the kernel's contract for tools; BPF_F_FAST_STACK_CMP as documented (the hash includes nr); returning the id of a trace being replaced or deleted is the kernel's behaviour too. Memory is bounded by max_entries x record size, what the kernel commits upfront. `[stack_trace]` tests pass (S/runtime_tests.log).
- Ringbuf tag: 9 slot bits hold slots -1..255 (256 slots + none, static_assert), 22 fd bits hold MAX_MAX_FD_COUNT (static_assert; handler table default 6144); fds are shared handler-table indexes, the same in every process; padding is tagged slot -1 and never decoded; reserve/submit/discard/recover/test helpers encode and decode consistently, set_owner_slot_for_test keeps the fd; bpf_ringbuf_output passes the fd itself; libbpf's consumer reads only `len`, never the second word. The test "Ringbuf helpers submit and discard through the sample's map" exercises the helpers through the tag with fds that differ from slot numbers. `[ringbuf]` tests pass.
