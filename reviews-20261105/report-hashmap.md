## Findings (most severe first)

### 1. CLAUDE.md promises whole `lookup_read` copies; on 4-byte-key maps the code gives that only to readers that use acquire loads — medium (documentation claiming a guarantee the code does not give; current in-tree readers are correct)
- Commits: d16fcbf5 (the four-byte path's acquire fence after the key compare replaced by an acquire key load), fbcc1a04 (`lookup_read` API), 518a6b99 / ea32ad8b (the CLAUDE.md wording).
- Where: `runtime/src/bpf_map/bpftime_hash_map.hpp:588-596` — on a match, `read(value_of(e))` runs, then `if constexpr (!Uint32Key) atomic_thread_fence(acquire)`, then `load(word, relaxed) == w`. For 4-byte keys nothing orders the reader's loads before the word re-check. The header says so (lines 547-550: "it must read with acquire loads"), but CLAUDE.md "Hash Map Concurrency" states without qualification: "A `lookup_read` copy holds one value whole (the word re-check catches reuse)."
- Failure scenario: a reader that copies with plain loads (memcpy) on a 4-byte-key map; the element it stands on is the old element of a replaced key, the next update of the stripe reuses it as the spare and overwrites the value while the copy runs; the relaxed word load is satisfied before the copy's last loads, so the re-check passes and the torn copy is returned as whole.
- Evidence, reproduced: `plain_reader.cpp` (`timeout 30 ./plain_reader 3 <words>`; 2 updaters replacing one key's value `{x,x,...}`, 3 memcpy readers, 3 acquire-load readers). Output (`plain_reader.log`):
  `value 16 B: memcpy reader: 65486636 copies, 0 torn; acquire reader: 67659498 copies, 0 torn`
  `value 64 B: memcpy reader: 80282972 copies, 1 torn; acquire reader: 66985866 copies, 0 torn`
  `value 256 B: memcpy reader: 38650372 copies, 575 torn; acquire reader: 28171687 copies, 0 torn`
  (16 B does not tear because an aligned 16-byte `ldp` is single-copy atomic on this core.) The per-CPU hash's reader (`per_cpu_hash_map.hpp:80 slot_of`, an acquire load) and every test reader comply, so no tool is affected today; the trap is for the next reader of the API, and the doc is wrong as written.
- Fix direction: emit the acquire fence on the four-byte path only when the reader is non-empty (e.g. `if constexpr (!Uint32Key || !std::is_empty_v<std::remove_reference_t<Read>>)`), which keeps `elem_lookup` fence-free (the +4 ns d16fcbf5 removed), or state the acquire-load requirement in CLAUDE.md next to the claim.

### 2. Stripe spin lock has no fairness: a writer of a stripe whose lock another thread takes in a tight loop waits tens to hundreds of ms per update — concern, medium-low; pre-existing (the range narrowed it), not a regression
- Commits touching it: 0ffe368b / 49bc1fd9 (inline exchange-1 / store-0 lock), 68f19c1f; the protocol is glibc's generic `pthread_spin_lock`, which the stripes used before 0ffe368b and the single `map_lock` used before the striped table.
- Where: `runtime/src/bpf_map/map_common_def.hpp:38-60` (`bpftime_spin_lock`: exchange, then spin on a relaxed load with `yield`; no queue, no backoff), taken by `update`/`elem_delete`/`next_key` in `bpftime_hash_map.hpp`. The kernel's htab bucket lock is a fair qspinlock.
- Scenario: thread A updates a key of stripe S in a tight loop (replace path, ~35 ns under the lock); thread B (another thread of the traced process, or the tool) does one update of another key of S. B's exchange almost never wins the line back from the core that just released and re-takes it.
- Evidence, reproduced (`fairness.cpp`, `timeout 30 ./fairness <hammers> same|other 2 [gap]`; numbers are from a shared machine, qualitative only — `fairness.log`, `fairness_gap.log`, `fairness_pthread.log`):
  `gap 0 hammers 1 (4108510 updates/s) victim in the same stripe: 16 updates, latency ns p50 59896429 ... max 611899115` (victim tries one update every 50 µs for 2 s and gets 7-149 through, p50 2.6-216 ms over several runs);
  `hammers 2 ... same stripe: 31 updates, p50 3103811 ... max 521377047`;
  `hammers 1 ... another stripe: 17687 updates, p50 224 p99 864 max 475183` (fine);
  with the hammer doing work between updates: `gap 50 (3.8M updates/s): p50 320 p99 21118805 max 32245282`; `gap 200 (1.6M updates/s): p50 224 p99 1184 max 2720` (fine).
  The same test built against a shadow copy of `map_common_def.hpp` that calls `pthread_spin_lock` (the pre-0ffe368b protocol, `build_shadow.sh`, `shadow/`): `hammers 1 ... 14 updates, p50 107895069 max 351894533`; `hammers 2 ... 4 updates, p50 671893160` — worse, so the range did not introduce this. Realistic probe rates (Frida ~1 µs per hit, syscall hook ~0.4 µs) sit below the ~4M updates/s on one stripe where it appears; it also explains why `replace_long_keys` (below) got only 1,416-9,690 insert+delete cycles in 2 s from its third thread.
- Fix direction: a ticket or MCS-style lock for the stripes (one more word per line), or at least exponential backoff / `sched_yield` after N spins; document the limit otherwise.

### 3. A tool killed (or faulting) inside `next_key` or `lookup_and_delete` leaves the stripe locked for the traced process — low, by reading; documentation precision
- Commits: e5ba4aa7, b7ded27a (dead-holder paragraph), 7ad5a152.
- Where: `bpftime_hash_map.hpp:779-817` (`next_key` takes the stripe lock of the key's bucket and of each non-empty bucket it scans), `:754-773` (`elem_delete(key, value_out)` copies `_value_size` bytes into `value_out` under the stripe lock; through `map_lookup_and_delete_elem` (`map_handler.cpp:1803-1809`) `value_out` is the tool's `attr->value` pointer, so an unmapped buffer is a SIGSEGV with the lock held, where the kernel returns EFAULT). CLAUDE.md attributes stripe hangs to "A process killed inside a writer" and says "next_key calls reaching it hang" — the tool iterating with SIGKILL/OOM-kill mid-iteration is itself a holder, and then every writer of that stripe in the traced process (a BPF helper) spins forever while lookups go on. Same class as before the range (the handler's `map_lock` had it, worse), so low.
- Fix direction: name `next_key`/`lookup_and_delete` in that sentence; copy the value into a local under the lock and to the caller after unlocking.

## Checked, no defect found
- Lock-free lookup vs locked writers on aarch64 (`lookup_in_bucket`, `link_locked`, `replace_locked`, `unlink_and_retire_locked`): the walk's invariant holds given inserts only at the head, replacements in place keeping the key, deletes unlinking before retiring; the link re-check (link reloaded with acquire, then the word) closes the "element reached through an old link, word read after reuse further down" case, and a link that points to the element again after reuse can only do so in a position that skips no key present throughout (new head inserts may be missed, allowed). Release/acquire pairs: word (release) before link (release) in `link_locked`, acquire on head/next/word in the lookup, release fence before key/value writes paired with the acquire key load (4 B) or fence (memcmp). Generation ABA needs 2^31 retirements of one element inside one lookup. Stale `next` reads lead into free lists (`NULLS | n_heads`), other chains (foreign terminator) or non-used elements, all of which restart. Terminator `end` can only be read from a verified link.
- Torn keys: 4-byte keys are atomic loads; longer keys that match half-overwritten bytes are caught by the word re-check through the fence pairing (and the existing 64-byte torn-key test).
- Dead holders: a deleter stopped between unlink and retire leaves an unreachable, in-use element (leak, no restart storm); an updater stopped after the link store, an inserter stopped after taking an element: leak, stripe locked either way, lookups never wait. Matches CLAUDE.md apart from finding 3.
- Free lists and E2BIG: lock order stripe → list only; spares are outside `max_entries` and never counted; `get_elem_count` exact when quiescent. `capacity.cpp` (6 threads inserting 21,200 keys into 20,000 entries, free elements spread or all on one list): 5/5 rounds `failed 1200 (expect 1200) count 20000`; with 3 threads deleting and re-inserting at capacity: `91970700 delete+insert, 0 spurious E2BIG` (the documented pcpu_freelist window, not reproduced).
- Update modes: BPF_ANY/BPF_NOEXIST/BPF_EXIST and E2BIG/EEXIST/ENOENT/EINVAL as the kernel's htab, in one locked operation; an existing key always goes to the stripe's spare, a value pointer stays on the old element (kernel's extra_elems has the same reuse window).
- Iteration: `next_key` equals `htab_map_get_next_key` (next in chain, else first of the following buckets; missing key restarts at bucket 0); replacements keep chain order so updated keys are not returned twice. Under churn every pass finished and saw every present key.
- Seed: `hash_zero_seed` tests `1u << 6` on the map flags and the env var in the creating process; `_seed` lives in the shared map object; the collision test and the three-map order test are sound.
- Syscall `BPF_MAP_LOOKUP_ELEM` copies from the returned pointer without a lock: the same tear window as the kernel's prealloc reuse; `lookup_and_delete` copies under the lock.
- x86 lock protocol (pthread there, 49bc1fd9), spin-lock test claims, element/value alignment, constructor bounds (`max_entries`, heads, `_num_elements` < NULLS, overflow checks), `my_list` from the thread pointer across dlmopen namespaces.
- Real tools: funclatency/syscount/memleak patterns (lookup-or-create with BPF_ANY/NOEXIST, atomic add through the pointer, update+delete per call, tool-side get_next_key + lookup + delete) behave as with the kernel; the only semantic differences are in bpftime's favour (no miss of a key being updated, no re-visit of updated keys).
- Existing tests at 94f9ba8f pass on `build-jetson-daily`: `[bpftime_hash_map]` 27 cases, `[hash]`, `[spin-lock]`, `[hash-seed]`.
