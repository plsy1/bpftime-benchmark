### 1. libbpf's third poison form (CO-RE relocation failure, imm 195896080 / 0xbad2310) is neither rewritten nor treated as a missing helper
- severity: low
- commits: 74d0ab8b, 94f9ba8f
- files: `runtime/src/bpftime_prog.cpp:485-489` (`is_libbpf_poison_call`: only 2001000000..2002999999), `:590-597` (`missing_helper` requires `imm < BPFTIME_DEAD_CALL_SLOT`, so 195896080 is excluded); CLAUDE.md "Failed JIT Compiles" lists only the 2001/2002 forms.
- what is wrong: libbpf's `bpf_core_poison_insn` (third_party/libbpf/src/libbpf.c, relo_core path) turns an instruction whose CO-RE relocation failed (e.g. a `BPF_CORE_READ` of a field absent on this kernel, guarded by `bpf_core_field_exists`, which libbpf resolves to `mov r, 0`) into `call 195896080`, both halves of an ldimm64 included. The kernel prunes it; bpftime still fails the compile (`Ext func not found: _bpf_helper_ext_195896080`) and disables the program, and the rodata analysis is not even run for it.
- failure scenario: any libbpf-tool program with a `bpf_core_field_exists()`-guarded access to a field the running kernel lacks is disabled.
- evidence: reproduced on this box's logs: `/home/jetson/src/results/uprobe/memleak-fix-20261104/detach-manual/dev-ff5515d8.memleak.t1.workload.txt` lines 60-69 (`JIT compilation of memleak__kmalloc/kfree/kmem_cache_* failed (Ext func not found: _bpf_helper_ext_195896080); the program is disabled`). Those are memleak's tracepoint programs, which bpftime cannot attach anyway, so no tool loses data today; the commit message/CLAUDE.md claim about "calls libbpf poisoned" is incomplete rather than a tool regression.
- fix direction: extend `is_libbpf_poison_call` with `imm == 195896080` (point it at the same private slot) and mention the form in CLAUDE.md.

### 2. kfunc calls (`src_reg == BPF_PSEUDO_KFUNC_CALL`) in dead code still disable the program
- severity: low
- commit: 94f9ba8f
- files: `runtime/src/bpftime_prog.cpp:590-597` (`missing_helper` requires `src_reg == 0`); `vm/llvm-jit/src/compiler.cpp:1366-1371` only distinguishes `src == 1`, so a resolved kfunc call is compiled as helper `_bpf_helper_ext_<btf_id>` (`compiler_utils.cpp:368` "Ext func not found").
- what is wrong: when vmlinux BTF has the kfunc, libbpf emits `src_reg=2, imm=btf_id`; such a call can never be registered, yet the analysis does not consider it "missing", so an off-option branch calling a kfunc keeps the whole program disabled. CLAUDE.md says "a helper nobody registered", which does not cover this.
- evidence: by reading; none of the libbpf-tools in `/home/jetson/src/realprog-20261026-btf/libbpf-tools/*.bpf.c` declare `__ksym`, so no tool here is affected.
- fix direction: let `missing_helper` also match `src_reg == 2` and rewrite unreachable ones to the dead slot (the JIT already treats imm as the helper index).

### 3. AOT objects compiled from a program with poisoned/dead calls reference the private slots, which the AOT loader never registers
- severity: low
- commits: 74d0ab8b, 94f9ba8f
- files: `tools/aot/main.cpp:93,124` call `bpftime_prog_load(true)` (applies both rewrites) before `do_aot_compile`; `runtime/src/bpftime_prog.cpp:875-888` (`load_aot_object` only runs `register_pending_map_helpers`); `vm/llvm-jit/src/llvm_jit_context.cpp:771-790` defines ext symbols only from `vm.ext_funcs`.
- failure scenario: `bpftime aot` of opensnoop-like code now succeeds and writes an object calling `_bpf_helper_ext_8188`/`8187`; loading it in the agent cannot resolve those symbols (load fails). Before the commits the AOT compile itself failed, so nothing regresses; CLAUDE.md only says AOT-loaded programs skip the rewrites.
- evidence: by reading.
- fix direction: register `BPFTIME_LIBBPF_POISON_SLOT`/`BPFTIME_DEAD_CALL_SLOT` helpers in `load_aot_object` too (cheap, idempotent).

### 4. Freeze blocks fewer syscall-side writes than the kernel
- severity: low
- commit: 94f9ba8f
- files: `runtime/src/handler/map_handler.cpp:445,776` (only update/delete check `is_frozen()`); `runtime/src/bpftime_shm_internal.cpp:384-401` (`bpf_map_push_elem`/`pop`/`lookup_and_delete` ignore it); `runtime/syscall-server/syscall_context.cpp:1001-1007` (`handle_mmap64` returns the raw array value pointer regardless of `prot`/`MAP_FIXED`).
- what is wrong: the kernel's `map_get_sys_perms` drops FMODE_CAN_WRITE for frozen maps for every write command and refuses `mmap(PROT_WRITE)`; here a frozen queue/stack/hash map still accepts push/pop/lookup_and_delete from the syscall, and libbpf's post-freeze `mmap(map->mmaped, PROT_READ, MAP_SHARED|MAP_FIXED, fd)` of `.rodata` (libbpf.c:5281-5290) hands the tool a writable pointer into the frozen constant. Only matters for tools that would crash/EPERM on the kernel (no real tool writes `skel->rodata` after load), so the constant-folding stays sound for kernel-accepted tools.
- evidence: by reading.
- fix direction: check `is_frozen()` in push/pop/lookup_and_delete when `from_syscall`; honor `prot` in the array mmap path (or document).

## Checked, no defect found
- Analysis soundness (`runtime/src/bpftime_prog_reachability.cpp`): modeled ALU32/ALU64 ops zero-extend/sign-extend exactly as the kernel (imm sign-extended for ALU64 and JMP64, truncated for ALU32/JMP32; shifts masked; mul/add/sub wrap); `off != 0` (movsx, sdiv/smod), MEMSX loads, bswap, neg, arsh, div/mod leave registers unknown; `ja` uses off, `gotol` uses imm; may_goto/unknown jump ops are undecided; calls (any src_reg) clobber r0-r5 and keep r6-r9 (the llvm JIT saves/restores r6-r9 on local calls, compiler.cpp:1420-1460); bpf-to-bpf targets and `BPF_PSEUDO_FUNC` callbacks (`pc+imm+1`, matching the kernel) are entries with unknown registers; LD_ABS/IND clobber r0-r5; atomics with FETCH/CMPXCHG clobber src/r0; stack never tracked (r10 unknown); ldimm64 src 1/3/5/6 unknown; map_value pointer arithmetic only `add64 imm`, loads bounds-checked against the value size, little-endian host.
