# x86 NUC：dev d5279469（hash map 重写）的测试和测量（2026-11-03 晚）

Jetson 会话 bpftime-arm64环境-性能优化 转达的用户请求：在 x86-64 上验证并测量重写后的 hash map。开发分支 `dev/uprobe-official-177a1dc465ff` 从上次在 x86 上验证的 `42595149` 到 `d5279469`。按 NUC 的规矩只测不改，开发分支没有改动。

- 改动（`42595149..d5279469`，10 个提交）：`bpftime_hash_map` 改写成内核预分配 htab 的样子，放在共享内存里用偏移表示：
  - u32 链表；查找不加锁，靠每个元素的代数字（generation word）检查读到的是否还是同一个元素；
  - 每次写只拿一把 stripe（分段锁的一段）自旋锁；
  - 空闲元素放在每个 CPU 一条的空闲链表里，空闲元素就是容量；
  - 两轮 review 的修复：删除先摘链再标记空闲；每个 map 一个随机哈希种子（`BPFTIME_HASH_ZERO_SEED=1` 或 map 标志 `BPF_F_ZERO_SEED` 时种子为 0）；更新已有的键写到备用元素里，不再原地写。
  - 之前只在 aarch64 上测过。它依赖内存序，aarch64 上用内联自旋锁，x86 上从 49bc1fd9 起调 `pthread_spin_lock`。设计说明在开发分支 CLAUDE.md 的 bpftime_hash_map 一节。
- 机器：`debian-ichi-nuc`，i5-1240P，Debian 13，内核 `6.12.113+deb13-amd64`，glibc 2.41。
- 时间：22:41 构建，22:43–22:47 测试，22:48–23:09 官方 uprobe 十轮，23:12–23:39 键模式矩阵。

## 0. 结论

- **测试：没有新的失败。** runtime 单测 245 个用例（每个限时 60 秒）：238 通过，7 失败，就是以前那 7 个（要 root 或没开统计选项），sudo 下要 root 的 4 个全过。请求的标签组合 61 个用例 59 过 2 跳过（要 root）。4 个并发压力测试一次就过，又各跑 20 次、满载下再各跑 20 次，140 次全过，没有读到不完整的副本（`tests/README.md`）。
  - 一点要交给 Jetson 看的：`hash map copies of keys updated behind the head are whole` 里只计数的漏查，x86 上每次 17–111,595 次（读的 0.000005%–0.13%），比 CLAUDE.md 里引用的复查结果（6,100 万次查找漏 4–8 次）多得多。测试不对它设上限。
- **官方 uprobe 十轮**（第 2 节）：和同场的 42595149 比，普通 hash lookup −10%（0.47× kernel），update +20%（0.35×，更新已有的键现在写备用元素，aarch64 上也是这样），delete −6%（0.43×）；per-CPU hash 按中位数在 ±3% 以内；其他用例在 ±2% 以内。
- **键模式矩阵**（第 3 节，删除 + 插入，经 BPF 程序）：一个线程时 map 开销是 kernel 的 0.42–0.79×；6 个线程时 0.63–1.08×（只有 10240 / 50% / addr 一格 1.08×）。种子让 8 字节地址键慢了 7–24%（一个线程）、6–28%（6 个线程），和 aarch64 的 11–28% 相近。
- 264 次矩阵运行、20 次十轮采样都通过了事件计数的校验；测前测后都没有残留进程和 root 拥有的 `/dev/shm` 段，频率设置已恢复。没有起容器。

## 3. 键模式矩阵（`keypattern/`）

- **方法**：Jetson 结果 `uprobe/hash-keypattern-20261103` 的矩阵（来源提交在 `jetson-source-commit.txt`）。`src/` 里的 `keyloop.c`、`keymap.bpf.c`、`attach.c` 和 `build.sh` 原样复制（哈希在 `src/jetson-sources-sha256.txt`，测前核对），只另写了 x86 的构建脚本 `src/build-x86.sh`（d5279469 构建目录里的 libbpf 1.7.0，clang-19，x86 目标）。构建出的二进制只放本机，哈希在 `artifact-sha256.txt`。
  - `run_keys.py` 相对原版只改了三处（文件开头有说明）：构建目录、名为 `<构建>-zeroseed` 的后端在两个进程里都设 `BPFTIME_HASH_ZERO_SEED=1`（map 由加载器在 syscall server 下创建）、`--patterns` 选择键模式。
  - 一次操作 = 查找并删除最老的键 + 插入一个新键，经 uprobe 上的 BPF 程序；没有更新已有的键。容量 10240 / 102400，负载 50% / 90%，键 `addr`（8 B 分散地址）、`seq64`（8 B，类似 pid_tgid）、`rand32`、`shl12`（4 B，id << 12），1 和 6 个线程。map 开销 = 用这个 map 的对象减去 `keymap-control.bpf.o`（同样的探针和 helper，不碰 map），同一后端、同一线程数，3 次的中位数。
  - keyloop 自己把线程绑到 CPU 5、4、…、0（3 个 P 核的两个线程）。`run.sh` 把这 6 个 CPU 钉在 3.5 GHz（turbo 开，min = max，C6 及更深关闭；几个核同时忙时 4.4 GHz 撑不住，同 ssl-nginx），测前 busy 检查通过（`log/check-before.txt`），E 核 15 每秒采样：6 个 CPU 忙碌 > 90% 的 3,888 个采样都在 3,515–3,521 MHz。plymouthd 测时绑到 E 核 12–14，测完改回。
  - 第一次启动时，root 拥有的 `/dev/shm` 段检查把 `/dev/shm` 目录本身也算进去了，还没测就拒绝启动，记录在 `first-try-refused/`。改成 `-mindepth 1` 后重跑。正式运行前用 1 秒的短跑在 scratchpad 里试过一次加载和计数（不计入结果）。
- **结果**：`summary.md`（`summarize.py`），原始数据 `keys.jsonl`（204 次，kernel 和 d5279469）、`keys-zeroseed.jsonl`（60 次，addr，有种子和种子为 0），全部计数精确。
  - 控制组（每次操作的探针本身）：kernel 一个线程 2.81 us、6 个线程 4.27 us；d5279469 0.33 us、0.61 us。x86 上 kernel uprobe 本身就贵，kernel 的 map 开销是从 2.8–4.3 us 里减出来的，精度有限。
