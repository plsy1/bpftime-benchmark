# Dimension coverage: problems found (running list)

Collected while running the dimension benchmarks (plan: `map-usage-20261027/README.md`); fixes
are planned together once the matrix is done. Each entry: what, evidence, where in the code.

| # | Problem | Evidence | Code |
|---|---|---|---|
| 1 | Hash maps serialize all threads on one spinlock, lookups included; cost per call grows from 0.12 us (1 thread) to 6.3 (4 threads, two clusters) and 10.7 (6); kernel 0.2-0.4; tracking table (memleak pattern, 1K-900K entries) 0.5 -> 10.5-11.6 us at 6 threads; hash counters that only look up + atomic add 0.03 -> 1.4 us | `map-threads-20261028`, `map-table-20261028` | `bpf_map_handler::map_lock`, `map_lookup_hash` / `map_update_hash` / `map_delete_hash` |
| 2 | The probe path without maps degrades with threads: 0.21 us (1 thread) -> 1.25 (4, one cluster) / 2.25 (4, both clusters) -> 4.54 (6), kernel 4.19 at 6. **Cause found:** Frida's interceptor increments and decrements a per-function `trampoline_usage_counter` atomically on every hit (83% of that function's samples at 6 threads on those two loops; IPC 2.82 -> 0.14). The counter only serves detach (free the trampoline when no thread is inside) | `map-threads-20261028`, `map-table-20261028`, `map-scratch-20261028` (controls); `probe-path-profile-20261028` | frida-gum `_gum_function_context_begin_invocation` / end_invocation (`trampoline_usage_counter`), bpftime `uprobe_listener_on_enter` |
| 3 | Lookup returns a pointer after releasing the map lock and updates copy in place, so a program can see the value change while reading it. **Measured:** bpftime 6-10 torn reads per million reads (one writer, 1-5 readers, helper call between two loads); the kernel tears too (0.1-2.8 per million, prealloc or not), since it reuses replaced elements at once. Within kernel semantics, only more frequent | `map-torn-20261028` | `map_lookup_hash`, `bpftime_hash_map` in-place update |
| 4 | **Fixed (dev `cdc05f67`, `c98951a4`).** Per-CPU hash crashed the traced process on concurrent inserts: no lock anywhere (`should_lock = false`, same in official 177a1dc465ff); 64 keys, 2-6 threads: 6 of 9 runs died (5 SIGSEGV, 1 hang). Also found: the program-path update ignored `BPF_NOEXIST`/`BPF_EXIST` (a racing insert overwrote the winner: one lost count) and had no size limit for keys other than 4 B. After the fixes 48/48 runs valid; lock cost with threads 0.2-0.6 us per call | `map-table-20261028` (counters), `percpu-hash-fix-20261028` | `per_cpu_hash_map_impl`, `map_update_percpu_hash`, `map_lookup_percpu_hash` |
| 5 | **Recorded, not fixed (user decision).** A process that dies inside the shared segment leaves its locks held: map spinlocks forever (every later user of the map spins at 100% CPU), Boost mutexes permanently `lock_exception`. Measured: SIGKILL of a traced process at a random moment hung the loader reading that hash map in 7 of 40 trials (gdb: `pthread_spin_lock` in `bpf_map_get_next_key`). The first sighting (loader `lock_exception` after the per-CPU hash crash) was probably shared-memory corruption by problem 4, now fixed. Specific to running map code in the traced process: kernel map code always completes before SIGKILL takes effect. Options (robust mutex + disable, or crash-consistent updates + take over, as LMDB) in the README | `map-table-20261028`, `dead-holder-20261028` | `bpf_map_handler::map_lock` (`pthread_spinlock_t`), Boost segment mutexes |
| 6 | Single-thread probe overhead: every hit pushes a Frida invocation stack entry into a zero-initialized `GArray`, clearing a ~3 KB `GumInvocationStackEntry` (memset 14.5% + GArray resizing ~7% of the 0.21 us hit at 1 thread) | `probe-path-profile-20261028` (t1) | frida-gum `gum_invocation_stack_push` (`g_array_sized_new (FALSE, TRUE, ...)`) |
