## 3. Why (Catch2 3.4.0 source and docs)
# reporters/catch_reporter_junit.cpp:91  m_preferences.shouldReportAllAssertions = true;
# internal/catch_run_context.cpp:173    m_includeSuccessfulResults = includeSuccessfulResults()
#                                        || shouldReportAllAssertions
# A passing assertion then takes the full path (RunContext::handleExpr -> reportExpr ->
# assertionEnded): builds an AssertionResult (std::string members), copies the message vector
# into AssertionStats for the reporter and move-assigns the result to RunContext::m_lastResult. Without it (plain console) a
# pass only does ++m_totals.assertions.passed and clears an empty vector: still a data race on
# the counter, but nothing allocated or freed. Several threads on the full path allocate and
# free shared RunContext and reporter state at once -> heap corruption (which allocation is
# freed twice was not traced).
# docs/limitations.md, "Thread safe assertions": "Catch2's assertion macros are not thread safe.
# ... only single thread can interact with Catch's assertions and other macros." Opt-in
# thread-safe assertions came in Catch2 3.9.0 (CATCH_CONFIG_EXPERIMENTAL_THREAD_SAFE_ASSERTIONS),
# renamed CATCH_CONFIG_THREAD_SAFE_ASSERTIONS and no longer experimental in 3.12.0.

## Conclusion
# The test code breaks Catch2's documented rule (one thread at a time in assertion macros); the
# bpftime runtime is not involved. Plain console runs (the daily, each.sh, upstream CI's
# test-runtime.yml, the NUC per-case runs) do not report passing assertions and so do not crash.
# x86 not rerun: its whole-suite junit runs died right after the LPM trie cases, which fits.
# A failing REQUIRE in one of these worker threads aborts the whole binary (exception out of a
# thread) on any reporter, instead of reporting the failure.
