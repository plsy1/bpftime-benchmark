# Many probes in one program (2026-11-06)

Item 4a of the extra dimensions (`../README.md`). Kernel `6.8.12-1021-tegra-btf`, bpftime
`fix-final` (dev d46ceb8f). cpu5 at 1728000 before and after; 14:37-14:43 (`../go-rest.log`);
no other runs.

## Setup (`run.py`; programs in `../n2-startup/src`)

`many-M` (generated by `many.py`) has M functions f0..f(M-1), each long enough for Gum's
redirect. The tool (outattach) attaches out-control's program to all M (M = 1, 10, 100, 1000).
Per cell: the tool's time from start to "attached" (polled every 50 ms; outattach also waits
up to 100 ms for its own output); 50 starts of `many-M start` (calls nothing) through
`spawnloop`; `many-M run 3` (f_i round robin on CPU 5) for ns per call and its VmRSS at the end.
Checks: hits == calls. 2 reps; backends none, kernel, fix-final.

## Findings

| M | start p50, none / kernel / bpftime (ms) | ns per call, none / kernel / bpftime | VmRSS kernel / bpftime (MB) | tool attach kernel / bpftime (s) |
|---:|---|---|---|---|
| 1 | 0.49 / 0.50-0.51 / 22.8-23.4 | 1.5 / 1,241-1,250 / 222-223 | 1.4 / 38.4 | 0.10 / 0.20 |

| 1,000 | 0.50 / 3.43-3.44 / 438-441 | 8.3 / 1,303-1,314 / 295-303 | 1.5 / 39.6 | 0.30 / 0.50 |

**1. Every probe costs each new process 0.42 ms under bpftime (the kernel 3 us).** The agent
hooks every attached function in every process it starts in (Gum writes each redirect and
builds its trampoline before `main`): 1,000 probes delay a process start by 0.44 s. The kernel
inserts its breakpoints when the binary is mapped. Tools that attach many uprobes
(`bpftrace 'uprobe:libc:*'`, funccount on a library, USDT-heavy runtimes) make every traced
process start that much later, on top of item 2's 22-27 ms.

**2. The call itself does not care how many probes there are** (222 -> 299 ns from 1 to 1,000,
the untraced loop 1.5 -> 8.3 ns: the round robin over more code), as the kernel (1,245 ->
1,309).

**3. A traced process carries about 38-40 MB more resident memory** (VmRSS 38.4-40.3 MB
against 1.4-1.5 MB), whatever M: the agent (part 5 breaks it down).

The kernel tool with 1,000 uprobes took over 60 s to exit (detaching them), so the runner's stop
timed out and the two kernel M = 1,000 cells have no hit count (the rest of those cells, from
the workload, is complete).
