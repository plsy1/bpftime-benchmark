## Completed Works

### 1. Corrected the benchmark semantics

- **Lookup-hit/miss:** an existing key returns a value pointer; a missing key returns `NULL`.
- **Update-existing/insert:** an existing key is overwritten; a missing key creates a new entry.
- **Delete-hit/miss:** an existing key is successfully removed; a missing key returns an error and removes nothing.

| Benchmark operation | Actual measured semantics |
|---|---|
| Array lookup | Stable lookup-hit because array slots are preallocated |
| Hash lookup | Stable lookup-hit because hash update creates keys before lookup |
| Array update | Stable update-existing because array slots already exist |
| Hash update | Steady-state update-existing; `BPF_ANY` inserts only during the first call, about 0.001% of all helpers |
| Hash delete | Stable delete-hit after restoring keys outside the timed region before every sample |
| Array delete | Unsupported error-return path; excluded from performance comparison |

The same semantics apply to the corresponding per-CPU map cases.

**Ordinary array update is the only winner reversal:** both platforms use the same kernel C implementation. The relevant copy helper is declared `static inline`:

```c
static inline void bpf_obj_memcpy(struct btf_record *rec,
                                  void *dst, void *src, u32 size,
                                  bool long_memcpy)
{
    if (IS_ERR_OR_NULL(rec)) {
        if (long_memcpy)
            bpf_long_memcpy(dst, src, round_up(size, 8));
        else
            memcpy(dst, src, size);
        return;
    }

    /* Copy the non-special fields between the BTF-record fields. */
    ...
}
```

The difference appears only after compilation: ARM64 inlines this helper into `array_map_update_elem` and reaches `__memcpy` directly, while x64 retains the out-of-line path `array_map_update_elem → bpf_obj_memcpy → memcpy_orig`. This explains the direction of the winner reversal.

### 3. Identified the major cost paths on Jetson

The diagnostic layers follow the BPFtime map-helper execution path:

```text
L3 production helper called by JIT
  → L2 shared-memory map-fd lookup and variant dispatch
    → L1 generic map handler
      → L0 concrete array/hash map implementation
```

- **L0:** the concrete map operation, such as array access or hash find.
- **L1:** the generic lookup/update/delete handler and map-type dispatch.
- **L2:** shared-memory fd lookup, `offset_ptr`, and variant extraction.
- **L3:** the complete production helper entry used by the JIT-compiled BPF program.

The layers are cumulative diagnostic variants. Adjacent differences approximate the cost added by each layer; LTO and inlining mean the values are not required to increase monotonically.

For ordinary maps, hash update and hash delete were not investigated further because BPFtime was already faster. Array delete was excluded because the operation is unsupported. The remaining three kernel-winning operations were analyzed individually. All valid per-CPU operations were also analyzed because they were slower than kernel BPF.

The table reports costs measured inside BPFtime's diagnostic paths; it is not a strictly additive decomposition of the top-level BPFtime–kernel gap.

| Operation | Major internal BPFtime cost | Measured internal contribution |
|---|---|---|
| Ordinary array lookup | Generic handler plus shared-memory fd/variant dispatch | L1 and L2 add 9.72 ns/op above L0; 84 of the 98 cumulative L2 instructions |
| Ordinary array update | The same generic userspace dispatch around a small array update | L1 and L2 add 12.11 ns/op above L0, about 81% of the cumulative L2 time |
| Ordinary hash lookup | Userspace spin lock and trace logging; generic `memcmp` and repeated division in linear probing | 13.55 ns outer-path effect plus 12.06 ns lookup fast-path effect |
| Per-CPU array lookup | Userspace CPU selection, `std::function`, generic handler, and shared-memory dispatch | About 20.3 ns of the 21.0 ns control-adjusted L2 cost |
| Per-CPU array update | `std::function`/shared-memory value access plus generic handler and SHM dispatch | 32.43 ns function/copy block plus 26.56 ns L1/L2 dispatch |
| Per-CPU hash lookup | Boost.Interprocess key/vector representation and unordered-map hash/find | Hash find adds 91.29 ns, about 81% of the L0 net cost |
| Per-CPU hash update | Boost hash/find followed by shared-memory per-CPU value-vector copy | 91.16 ns hash find plus 61.35 ns value copy, about 85% of the L0 net cost |
| Per-CPU hash delete | Synchronous vector/node destruction and Boost.Interprocess shared-memory reclamation | 850.57 ns, about 85.4% of the synthetic delete net cost |

## Current Conclusion

- Ordinary map behavior is operation-dependent; BPFtime is not always slower.
- Per-CPU operations are consistently slower than kernel BPF on both platforms.
- The ARM64/x64 reversal in ordinary array update mainly comes from a much lighter ARM64 kernel path.
- The layered tests identify the dominant internal costs in BPFtime's map-helper path; a strict end-to-end attribution of the BPFtime–kernel gap remains separate work.
