# 多线程 hash map：调研（2026-10-29）

下一阶段的主线（10/30 组会）：bpftime 的 hash map 在多线程下很慢。本文整理现状、约束、可参考的设计和候选方案，
供定方案用。数据来自 `benchmark-results/jetson` 的 `uprobe/dimension-plan.md`、`dimension-problems.md`。

## 1. 问题

按真实工具的 4 类模式做的受控测试（Jetson Orin，每次触发探针的 map 开销）：

| 模式 | 内核 1 线程 | bpftime 1 线程 | 内核 6 线程 | bpftime 6 线程 |
|---|---:|---:|---:|---:|
| 入口插入、返回时查找加删除 | 0.20 µs | 0.12 µs | 0.32 µs | **10.72 µs** |
| 追踪表，90 万条 | 1.08 µs | 0.76 µs | 0.75 µs | **11.62 µs** |
| 共享计数，hash map | 0.02 µs | 0.03 µs | 0.02 µs | **1.36 µs** |

- 单线程 bpftime 更快；多线程只要用 hash map 就严重变慢，数组没有问题。
- 4 线程同簇 2.68 µs、跨簇 6.29 µs：Orin 两个簇之间传缓存行很贵，锁所在的那条缓存行在簇间来回跳。
- 共享计数这一类只做查找（加原子加一），也随线程数变慢：**查找也要拿锁**。

## 2. bpftime 现状

代码：`runtime/src/bpf_map/bpftime_hash_map.hpp`（上周已改过数据结构）、`runtime/src/handler/map_handler.{hpp,cpp}`。

- **结构**：开放寻址加线性探测，桶数为 `2 × max_entries` 以上的素数。每个桶是"4 字节状态 + key + value"，内联存放；
  状态有空、已用、已删除（墓碑）三种。元素**永远不移动**，因为查找返回的是指向桶内 value 的指针。
- **锁**：每个 map 在 handler 里有一把 `pthread_spinlock_t map_lock`，查找、更新、删除都拿。
  用 `pthread_spin_init(&map_lock, 0)` 初始化（"进程私有"），但它放在共享内存里，因为 glibc 的自旋锁就是一个 int，碰巧能跨进程用。
  锁里没有记录持有者，持锁进程被杀后检测不出来（问题 5，已记录未修）。
- **全表共享的可变状态**：元素个数 `_count`、最大探测距离 `_max_displacement` 和按距离的统计数组，每次插入删除都改。
  就算把锁拆细，这些也会变成新的争用点。
- **更新已有 key 是原地 `memcpy`**：读者可能读到写了一半的值（问题 3，实测每百万次读 6～10 次；内核也有，0.1～2.8 次）。
- **哈希函数**：4 字节 key 用固定系数的多项式，其他用 `hash*31`，没有随机种子。

## 3. 约束（和普通进程内并发哈希表不同的地方）

1. **共享内存、跨进程**：map 在 Boost.Interprocess 的共享内存段里，各进程映射到不同地址。结构内部只能用偏移或下标，不能存指针。
2. **读者是任意线程**：探针在被追踪程序的任意线程里触发，线程可能在系统调用里睡很久，也可能被杀。读者路径要极便宜（每次触发都走）。
3. **语义要和内核一致**：
   - 查找返回 value 指针，程序在调用返回后还会读写它；
   - 内核对这个指针也不保证稳定：预分配元素删除后立刻放回空闲链表，可能马上被别的 key 复用；
   - update 的 `BPF_ANY`/`BPF_NOEXIST`/`BPF_EXIST`、delete、`get_next_key` 遍历。
4. **固定容量、预分配**：`max_entries` 在创建时确定，元素存储预先分配，map 在使用期间不会被解除映射。
5. **进程可能被 SIGKILL**：不能因为一个进程死在临界区里，让其他进程永远卡住。
6. **ARM64 内存模型**：发布、读取都要有正确的 acquire/release，不能依赖 x86 的强序。

## 4. 参考设计

### 4.1 Linux 内核 htab（6.8.12，`kernel/bpf/hashtab.c`）

- **结构**：拉链法，`struct bucket { hlist_nulls_head head; raw_spinlock_t raw_lock; }`，桶数为 2 的幂。
- **查找不加锁**：程序本来就在 RCU 读侧里，直接遍历链表比较 hash 和 key。链表末尾不是 NULL，而是"nulls"值（记着桶号）。
  读者走到末尾发现桶号不对，说明中途经过的元素被删除并复用到了别的桶，就重新查一遍。
- **写入**：只锁一个桶。每个 CPU 有一个"正在持锁"计数，同一个 CPU 重入（比如持锁时又触发了 tracepoint 程序）直接返回 `-EBUSY`，不死锁。
- **更新已有 key**：从 per-CPU 的备用元素里拿一个，填好新 key 和 value，挂到链表头，再摘掉旧元素。之后的查找看到的是完整的新值，不会看到写了一半的值。
- **预分配模式下删除立即复用**：元素放回 per-CPU 空闲链表，不等宽限期。因为元素内存始终是有效的 htab 元素，读者踩到被复用的元素也不会访问非法内存，最多重查。
- **计数**：元素多时用 per-CPU 计数器（每批 32），避免所有 CPU 抢一个原子变量。

**启发**：预分配加"元素内存始终有效"，查找就**不需要宽限期**。而"用户态跨进程没有宽限期"恰恰是最大的难点，这样就绕过去了。

### 4.2 DPDK rte_hash 的无锁读模式（`RTE_HASH_EXTRA_FLAGS_RW_CONCURRENCY_LF`）

- 布谷鸟哈希，每个桶一条缓存行、8 个槽：16 位短签名加 key 存储区的下标；key（和 8 字节数据）放在单独的存储区。
- **读者**：先读一个全表的"变更计数"，扫主桶和备桶，签名匹配再比完整 key。命中直接返回；**未命中**时重读计数，变了就整个重查。
- 计数只在布谷鸟搬移时加，普通插入和删除不加：它只防"key 搬移过程中短暂地不在任何一个桶里"导致的假未命中（MemC3 里同样的问题）。
- **写者**：单写者，或者多写者时拿一把读写锁。
- **回收**：删除只清桶里的槽，key 存储区的下标要等所有读者都不再引用才能复用，靠应用自己判断，或者接 QSBR（见 4.4）。
- **跨进程**：要求所有进程把大页映射到**相同的虚拟地址**，结构里全是指针，不能直接用于 bpftime。
- 值只有 8 字节或一个指针，库本身不支持"返回值指针、原地修改"。

### 4.3 MemC3、libcuckoo、Folly、TBB

- **MemC3（NSDI'13）**：4 路布谷鸟，单写者；8192 个按 key 哈希分组的版本号。写者搬移前后各加一，奇数表示正在搬移；
  读者先读版本号（奇数就等），读两个桶，再核对版本号，变了就重读。**读者不写任何共享数据。**
- **libcuckoo**：分段自旋锁（最多 65536 把），但查找要锁两个桶，读者不是无锁的。
- **Folly ConcurrentHashMap**：读者无等待，写者分片加锁，靠 hazard pointer 回收；`AtomicHashArray` 是固定数组、key 当锁、
  删除留永久墓碑（删除多的 BPF map 会被填满）。
- **TBB concurrent_hash_map**：每个桶一把读写锁加每个节点一把锁，读者至少两次原子写，而且锁的作用域到访问器析构为止，和"指针在调用后继续用"的语义不合。

### 4.4 内存回收：QSBR、epoch、hazard pointer

- DPDK `rte_rcu_qsbr`：每个读线程一个计数槽，结构里没有指针，理论上能放进不同地址映射的共享内存；
  但读者要注册线程号，**读者死掉后，写者等宽限期会永远等下去**，DPDK 没有活性检查。
- liburcu：所有变体的读者状态都在线程局部存储里，注册表是进程内的，`membarrier` 也只作用于本进程，**不支持跨进程**。
- Hazard pointer：每次访问一次写加一次栅栏，读者死掉后它占着的内存永远回收不了。
- **结论**：这些方案都会在共享内存里留下"每个读者的状态"，被 SIGKILL 的读者会卡住回收。
  bpftime 是固定容量、预分配、使用期间不解除映射的，用不上它们（见 4.1 的启发）。

### 4.5 持锁进程死掉怎么办

- **robust futex**：线程退出时，内核遍历它登记的 robust 链表，把锁字里还写着自己 tid 的锁标上"持有者已死"并唤醒一个等待者。
  glibc 2.39 进程启动时自己调用了 `set_robust_list`，每个线程只能登记一个链表头，所以 bpftime 想要内核帮忙，只能用 glibc 的
  **robust 进程共享互斥锁**（`PTHREAD_MUTEX_ROBUST`，48 字节；下一个加锁的人拿到 `EOWNERDEAD`，修复数据后调用 `pthread_mutex_consistent`）。
  适合写者，不适合读者路径。
- **自己做可恢复的自旋锁**：锁字里存持有者的 id，等太久就检查持有者是否还活着，死了就抢过来，再做修复。
  难点是"检查活着"：`kill(tid, 0)` 和 `/proc/<tid>` 会被 tid 复用骗过，换了 PID 命名空间（Docker）也不对。
- **LMDB 的办法**：在一个共享文件上，以 pid 为偏移加 1 字节的 `fcntl` 锁；进程死了内核自动释放这个锁，所以检查结果不受 tid 复用影响。
- PostgreSQL：自旋锁不可恢复，卡太久直接 PANIC，由主进程重启所有共享状态；DPDK 不处理。

## 5. 关键结论

1. **不需要内存回收机制**：bpftime 的 hash map 固定容量、预分配、使用期间不解除映射，过期的指针永远指向有效内存。
   需要的只是"读到的是一致的"，用版本号校验就能做到，不需要读者注册，也不需要宽限期。
2. **读者不写任何共享数据**：用版本号校验的读者既不会在簇间传缓存行，死了也不留下任何状态，不会卡住别人。
   这是相对读写锁、QSBR、hazard pointer 的决定性优势，也正是现在 6 线程慢的原因（读者也要写锁字）。
3. **写者按桶或分段加锁**，锁要能检测持有者死亡；修复要简单，所以发布必须是"一次 release 写"。
4. **全表共享的计数要拆开**（分片计数），否则写锁拆细了还会卡在计数上。
5. ~~更新已有 key 改成"写到备用槽再切换"~~（10/30 撤回：每次给计数器加一都要占一个空槽，更费；继续原地写，和内核 `BPF_F_LOCK` 一样，问题 3 维持只记录。）

## 6. 候选方案

所有方案的共同点：预分配存储只用 `uint32` 下标寻址；查找用版本号校验、不写共享数据；返回的 value 指针和内核预分配 map 一样"返回后不保证稳定"；写者锁桶或分段。

### A. 分组开放寻址 + 每组版本号（10/30 重新分析后不做，见第 8 节）

- 把桶分组，每组一两条缓存行：一个版本号、一把锁、约 8 个 1 字节的标签（key 哈希的高位），加槽下标或内联的 key + value。
- **读者**：读版本号（奇数就重试），在组内按标签找、比完整 key，拿到槽地址；acquire 栅栏后再读版本号，变了就重来。
  ARM64 上是两次 acquire 读加一条 `dmb ishld`。
- **写者**：锁组，版本号加一（变奇数），写进空槽，用一次 release 写发布标签或下标，版本号再加一。
- **删除**只清标签或下标，槽可以立刻复用。
- **更新已有 key**：写到备用槽再切换下标，和内核一样。
- **组满了**：探测下一组，并加一个全表的"搬移计数"（DPDK 的做法），让未命中的读者在有搬移时重查；或者改成两个候选组（布谷鸟）。
- **优点**：最接近现在的代码（开放寻址、内联、元素不移动），改动可以分步做，单线程性能不应变差。
- **难点**：组溢出时跨组的一致性；墓碑的处理。

### B. DPDK 式布谷鸟，改成偏移寻址

- 8 路桶存"16 位签名 + key 存储区下标"，key 和 value 放在单独的存储区；搬移时加全表变更计数；写者一把锁，或者分段锁加变更计数。
- **优点**：装载率最高，签名扫描局部性好；value 大（KB 级）时只搬下标，不搬数据。
- **难点**：key 存储区的槽何时能复用。要么立刻复用，再给每个槽加版本号、比完 key 后核对；要么交给加载器进程按跨进程的 epoch 回收。

### C. 照搬内核 htab

- 每桶一把锁，拉链加 nulls 标记，元素池预分配，空闲链表用"下标 + ABA 标签"实现无锁，可以按 CPU 分片（通过 glibc 的 rseq 拿 CPU 号）。
- **优点**：语义和内核最一致。
- **缺点**：要追链表指针（缓存不友好），而且每个元素还得加版本号，才能防止比较 key 时读到写了一半的值。

## 7. 要提前想好的难点

1. **持锁写者死掉**：留下一把锁和一个奇数版本号。两种办法：
   - 每段一把 glibc robust 进程共享互斥锁（内核帮忙，只用于写者）；
   - 锁字里存持有者的槽号，再用 LMDB 式的 `fcntl` 字节锁（共享文件上偏移 = 槽号）判断活性，不受 tid 复用和 PID 命名空间影响。
   - 修复者把版本号改回偶数，丢掉没发布的槽。读者看到版本号长时间是奇数时，应去检查持有者，而不是一直空转。
2. **程序通过指针原地写 value**：和内核一样会互相冲突；带 `bpf_spin_lock` 的 value 要有自己的锁（`BPF_F_LOCK`）。
3. **大 value**（KB 级）：方案 B、C 只搬下标，比 A 的内联方式好。
4. **C++ 内存模型下的版本号读者**：比较 key 时要用 relaxed 原子或 volatile 按字节读，栅栏位置参考 DPDK 的实现（`rte_cuckoo_hash.c:1716-1733`）。
5. **哈希函数**：现在没有随机种子，分布也一般。分组以后标签取自哈希高位，哈希质量更重要。
   （10/30：只有分组加标签才需要换哈希；按下标范围分段不需要，第 8 节的方案不换哈希，单线程数字不受影响。）
6. **per-CPU hash map** 现在也是整表一把锁（10/28 为了修崩溃加的），同样适用这套方案。

## 8. 定下的方向（2026-10-30 重新分析）

看了代码和数据之后，**不换数据结构，也不换哈希函数**，在现在的表上做改动。上面的 A、B、C 都不做，分组加标签留作以后的单线程优化。

### 8.1 预期更正

6 线程时，bpftime 去掉 map 的探针开销是 churn 4.77 µs、追踪表 5.62 µs。map 开销降到内核水平（约 0.3～0.5 µs）后，
总计约 5.1、6.1 µs，**低于内核的 6.68、7.64 µs**，也就是说只修 map 就能反超。`dimension-plan.md` 那句"只修一个不够"只对"只修 Frida"成立。
"总计 − 对照"不是线性可加的，最后看实测总耗时。

### 8.2 代码里确认的瓶颈

1. `bpf_map_handler::map_lock`：整表一把锁，查找也拿（`map_handler.cpp` 的 `map_lookup_hash` 等）。
2. `map_lock` 紧挨着每次查找都要读的 `map_impl_ptr`，在同一条缓存行：查找不拿锁，写者加锁解锁也会让读者失效。
3. `bpftime_hash_map` 的表头里，读者要读的（桶数、倒数、数据指针、最大探测距离）和写者每次都改的（`_count`、按距离的统计）混在一起。

### 8.3 不换结构的理由

- 元素永远不移动；`release_deleted_run` 只把后面跟着空桶的墓碑改回空，不会切断已有 key 的探测链。
  所以并发查找不会出现假未命中，只怕一件事：比较 key 时这个槽被删掉又插进别的 key，读到新旧混合的 key 字节。
- **每个槽已有的 4 字节状态字加代数**就能防住：低 2 位是状态，高 30 位是代数，删除时代数加一；插入先写 key、value，
  再用一次 release 写发布 `FILLED|代数`；读者 acquire 读状态、比 key、acquire 栅栏、再读状态，变了就重查。
  不多占内存、不多一条缓存行；读者不写共享数据，也从不等写者（写者死在中途最多留一个没发布的槽）。
- 分段按桶下标范围分，和哈希高位无关，现在的哈希够用。
- "删除时把后面的元素往前挪"不能用：会挪动 value，程序手里的指针就错了。

### 8.4 步骤（每步都有"不修就失败"的测试，并重测 churn、追踪表、共享计数，1～6 线程，同次运行对比内核和官方）

1. **查找不加锁**：状态字加代数；普通 hash 的查找不再拿 `map_lock`，写者仍用这把锁；锁挪到单独的缓存行，表头读写字段分开。
   预期共享计数回到平线；churn 的插入和删除仍抢一把锁，这一步的 churn 数字不代表最终效果。
2. **写者分段加锁**：约 64 桶一段，每段一把锁；最大探测距离按起始段分开记；跨段按下标顺序加锁、绕回有固定顺序、太长退回锁全部；
   向回清理墓碑在段边界停下；`_count` 改成按 CPU 分槽、分批汇总（单线程精确，接近满时走精确慢路径）。
3. 视数据决定是否继续（perf 找剩下的共享缓存行）。

不在这一轮：问题 3（撕裂读）、问题 5（持锁进程死掉，第 1 步只改善了读者一侧）、per-CPU hash（会重新哈希的 `boost::unordered_map`）、变长 hash。
另加多进程测试：多个进程共用一张固定住的 map。
