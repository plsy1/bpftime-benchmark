# Meeting - 20261030

## Achieved

Last week's plan had two directions: benchmarks with more dimensions, and real programs. Both are done; on the way, the ARM64 syscall path was implemented.

### 0. Real programs: compatibility audit and fixes

Ran real uprobe/USDT tools on bpftime and compared with kernel bpf: first 7 tools, then 18 after switching to a self-built kernel with BTF (libbpf-tools, bpftrace one-liners, sslsniff, USDT in the JVM).

- Several tools did not work on official bpftime at all (memleak, funclatency of libbpf-tools)
- Fixed them with 18 commits, spread over almost every component (uprobe attach, syscall server, runtime, maps, helpers, LLVM JIT)
- Now all 18 tools give **exactly the same counts as kernel bpf**

| Tool (throughput of the traced program) | bpftime / kernel |
| --------------------------------------- | ---------------: |
| funclatency                             |      3.1 – 3.6× |
| gethostlatency                          |            1.45× |
| memleak                                 |            1.28× |
| malloc example (printk on every call)   |            0.99× |

### 1. ssl-nginx end to end

- Map optimizations had no measurable effect here (+0.2% / +0.4%): the cost per event is in the uprobe entry/exit and perf output paths
- Fixed two correctness bugs: programs did not run in forked children (all nginx worker events lost); with 256 KB responses about half of the events were silently dropped (also in official)
- Removed two syscalls per event: `bpf_get_current_uid_gid` (2 syscalls) and `getpid`/`gettid` in perf output are now cached

| 16 B responses                  | Throughput        |
| ------------------------------- | ----------------- |
| bpftime vs kernel               | **+17.4%**        |
| bpftime vs no tracing           | −19.2%            |
| kernel vs no tracing            | −31.1%            |
| paper (x86): bpftime vs no tracing | −7.41%         |

bpftime is faster than kernel for every payload from 16 B to 256 KB (+11 – 17%).

### 2. Benchmarks with more dimensions

First counted how 16 real tools use maps at runtime (added an opt-in counter to bpftime): the most common pattern is insert at function entry, lookup + delete at return; keys 4/8 B; and **every tool was single-threaded**. Then built controlled benchmarks along these patterns with 1–6 threads, same-run kernel, and checked results.

| Threads (entry insert, exit lookup + delete) | Kernel | bpftime |
| -------------------------------------------- | -----: | ------: |
| 1                                            | 2.05 µs | **0.57 µs** |
| 2                                            | 3.01 µs | **0.97 µs** |
| 4                                            | 5.04 µs | 9.01 µs |
| 6                                            | 6.68 µs | 15.51 µs |

- Single thread: bpftime is faster, and its map operations are as fast as or faster than kernel bpf (key/value size, table size up to 900K entries, arrays, 8 KB per-CPU values)
- **Multiple threads are bpftime's weakness**. At 6 threads, about 10.7 µs comes from the hash map (one spinlock for the whole map, even for lookups), about 4.8 µs from Frida (an atomic counter on every probe hit, found with perf)
- Correctness: per-CPU hash maps crashed the traced program when several threads inserted keys (also in official) → fixed. Two more problems recorded: a killed process can leave a map lock held forever; per-CPU maps lose 1.4 – 2.3% of counts when threads are not pinned (kernel ≤ 0.09%)

### 3. Syscall tracing on ARM64 (new)

bpftime could not intercept syscalls on ARM64 (a TODO upstream since 2024). x86 uses zpoline, which does not work on ARM64; implemented a per-site trampoline after svc-hook (Middleware 2025), keeping every register intact. Each of 6 tests fails without its part of the change; with 1,000,000 writes, bpftime traced exactly as many as kernel bpf.

| Official syscall benchmark (10 runs) | Time per write | Overhead |
| ------------------------------------ | -------------: | -------: |
| No tracing                           |      353.45 ns |        – |
| Kernel tracepoint                    |      438.22 ns |   +85 ns |
| bpftime                              |      640.00 ns |  +287 ns |

- bpftime is slower than kernel here, as in the official x86 results (2.3× / 1.5× the kernel's overhead)
Broke bpftime's cost down by adding one layer at a time (5 rounds, medians):

| Layer added                                   | bpftime | Kernel |
| --------------------------------------------- | ------: | -----: |
| Rewritten instruction + trampoline + registers |  +38 ns |      – |
| Agent dispatch, no program for this syscall   | **+202 ns** | +15 ns |
| First program (empty)                         |  +42 ns | +69 ns |
| Second program (counting)                     |  +47 ns | +87 ns |

- The trampoline is cheap, and each program is cheaper than in the kernel
- **The agent's dispatch costs about 200 ns per syscall even with no program attached**: about 70% of bpftime's cost; this is shared C++ code on x86 and ARM64, so it is the target to optimize
- perf: about 970 extra instructions per syscall. For every syscall, even without a program, the dispatch heap-allocates a `std::function` twice (for the return-override helper) and accesses a non-trivial `thread_local` in the dlmopen-ed agent; only then does it check whether any program is attached

Same measurement on x86 (i5-1240P, zpoline), in CPU cycles so that the two can be compared:

| Layer added                                   | ARM64 (1.73 GHz) | x86 (1.7 GHz) |
| --------------------------------------------- | ---------------: | ------------: |
| Rewritten instruction + trampoline + registers |          65 cyc |       112 cyc |
| Agent dispatch, no program for this syscall   |     **349 cyc** |   **221 cyc** |
| First program (empty)                         |          73 cyc |        50 cyc |
| Official benchmark: bpftime / kernel overhead  |            3.4× |          3.9× |

- The dispatch is the largest layer on x86 too (57% of bpftime's cost; ARM64 72%), so fixing it helps both
- The ARM64 trampoline is cheaper than zpoline although it saves all 31 registers and the SIMD registers (zpoline probably slides through up to 511 nops for small syscall numbers; not measured separately)
- The new ARM64 code builds and passes all tests on x86, and zpoline still counts every call correctly

Fixed the dispatch: check for programs first and pass the syscall straight through without one; with programs, no heap allocation. Also fixed an out-of-bounds read for syscall numbers outside the table (`syscall(-1)` ran the wrong programs, 600 crashed). 4 new tests, each failing without its part of the change.

| Time per write (Jetson)                  |   Before |     After |  Kernel |
| ---------------------------------------- | -------: | --------: | ------: |
| Agent dispatch, no program for this call | +202 ns  | **+28 ns** |  +15 ns |
| Official benchmark (10 runs)             | 640.0 ns | **515.5 ns** | 437.8 ns |
| bpftime overhead / kernel overhead       |     3.4× |  **1.9×** |       – |

- What remains with a program attached is mostly the thread-local return-override callback (dynamic TLS in the dlmopen-ed agent, about 7% of samples); it is shared with the uprobe path, a separate change

### 4. DeepFlow (daemon mode)

Fixed 6 daemon-mode bugs (also in official) to run DeepFlow on ARM64.

| HTTP / HTTPS, 1 KB – 256 KB | bpftime vs kernel |
| --------------------------- | ----------------: |
| Throughput                  |   −1% to −28% |

- In daemon mode the maps stay in the kernel, so every map access of the moved uprobe programs is a syscall (only mmap-able arrays avoid it): 21% of the server's CPU
- The paper's "at least 1.5× faster" traces Go functions without syscalls, a different path
