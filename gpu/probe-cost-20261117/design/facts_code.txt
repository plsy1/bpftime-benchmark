2. ROUTING PASS (attach/nv_attach_impl/nv_thread_local_routing.cpp)
==================================================================
When it runs
- route_thread_local_maps_of_module (nv_attach_impl.cpp:985-1022) builds descriptors only for enabled 1530 maps: `if (!m.enabled || m.map_type != 1530 …) continue;` (:997).
  - fd = index, offset = (uintptr_t)extra_buffer, value_size, max_entries.
- It returns unchanged when there are none: `if (descs.empty()) return ptx;` (:1007-1008).
  - So the direct lookups, the r5 rewrite and the atomic guard exist only in a process with a 1530 map. Anything placed in route_function_body or guard_generic_atomics inherits this, and sees only 1530 descriptors.
- The kernel list is every kernel of every hook entry (:1009-1012).
- Area offsets (runtime/src/attach/bpf_attach_ctx_cuda.cpp:551-562): `local.extra_buffer = (void *)(uintptr_t)thread_local_bytes; thread_local_bytes += ((uint64_t)map.get_value_size() * map.get_max_entries() + 7) & ~7ull;`. Each map starts 8-aligned; entries are value_size apart.
- Size limit: THREAD_LOCAL_AREA_MAX = 1024 (nv_thread_local_routing.hpp:28; enforced in .cpp:392-396; the area is rounded to 8).

Step 1, kernels (.cpp:403-484)
- Each `…call… __probe_func__K;` or `__retprobe_func__K;` line becomes `<label>cvta.local.u64 %bpftime_tl, __bpftime_tl;` followed by `<pred>call …, (%bpftime_tl);` (:431-453). That is one cvta per site.
- Kernel prologue (:464-471): `.local .align 16 .b8 __bpftime_tl[N]; .reg .b64 %bpftime_tl; cvta.local.u64 …;`, then one generic `st.u64 [%bpftime_tl+off], 0;` per 8 bytes.
- It throws if any call of a routed function was not rewritten, e.g. a stub-replaced call in a device function (:486-501).
- A throw loads the module without probes: nv_thread_local_routing.hpp:48-49; hack_fatbin catches at :1189-1197 and returns nullopt at :1201-1204.

Step 2, probe functions (.cpp:503-533)
- Found by name prefix: `__probe_func__`, `__retprobe_func__`, `__memcapture__`, or `bpf_main` (:48-53).
- Routed functions (those called by a routed kernel) get `.param .b64 <name>_bpftime_tl` and `ld.param.b64 %bpftime_tl_in, […]` at body start, before the gate (:516-523; routed.ptx:7206-7218).
- Unrouted functions (memcapture, bpf_main) pass 0.

route_function_body (.cpp:293-382), per `{ // callseq … } // callseq` block
- Only helpers 1-3 are touched: `if (id < 1 || id > 3) { out += block; continue; }` (:325-329). 502 and all other helpers pass through.
- Direct lookup (:333-361): when the function is routed, id==1, and constant_fd() gives a 1530 fd, the callseq becomes
  `ld.u32 %bptl_k,[<param1 reg>]; setp.lt.u32 p,k,max_entries; mul.wide.u32 a,k,value_size; add a,a,%bpftime_tl_in; add a,a,offset; selp.b64 <retval reg>,a,0,p`
  - The key is loaded at run time through a generic pointer. That load is the "LD.E key" in the SASS.
  - The fd must be a constant; the key need not be.
- Other helper 1/2/3 calls: `st.param.b64 [param4+0], X` is replaced by %bpftime_tl_in (routed) or 0 (unrouted) (:362-378). It fails if param4 is missing or duplicated.
- Then guard_generic_atomics runs (:381).

Constant fd detection: constant_fd(), :119-157
- The operand of `st.param.b64 [param0+0], X` counts as constant if it is a decimal literal.
- Or if it is a register with exactly one definition `mov.[ub]64 X, <int>` and exactly one definition matching `(mov|ld|add|sub|cvt|selp|mul|and|or|shl|shr)\S* X,`.
- Gap: definitions by xor, neg, mad, min/max, rem, bfe, prmt and similar are not counted.

guard_generic_atomics (:159-291)
- Rewrites every `atom`/`red` without `.global`/`.shared` in a probe function:
  `add a,base,off; isspacep.local l,a; @!l <original>; @l ld.bN o,[a]; @l <op>; @l st.bN [a],n; @l mov dst,o`.
- Supported: add, and, or, xor, exch, cas at 32 and 64 bits. Others throw (:211-226), and so does a predicated atomic (:190-191).
- Applied regardless of where the address comes from. This is the QSPC in the SASS.
- Comment :159-164 cites PTX ISA 9.7.15.5. Its text (ptx-isa.txt:16801-16803): "atom with scalar type may be used only with .global and .shared spaces and with generic addressing, where the address points to .global or .shared space."

Shape evidence (kmr/routed.ptx; not llama)
- Key: `mov.u32 %r1, 0; st.local.u32 [%rd1+496], %r1;` (LLVM, via %SPL), then `ld.u32 %bptl_k0, [%rd3];` (routing). %rd3 = %SP+496 (`add.s64 %rd3,%rd14,496`, `add.u64 %rd14,%SP,0`, `cvta.local.u64 %SP,%SPL`).
- A u64 through a lookup pointer: `ld.u32 %rd60,[%rd59+32]; ld.u32 %rd61,[%rd59+36]; shl.b64; or.b64; … st.u32 [%rd59+32]; shr.u64; st.u32 [%rd59+36]`.
- Guarded atomic: `@!%bpat_l0 atom.add.u64 %rd134,[%rd133],1;`. %rd133 is a helper-1 retval, after `setp.eq.s64 %p10,%rd133,0; @%p10 bra`.

R3. The key's stack round trip
- The store is LLVM's (`st.local`; &key escapes into the 592-byte alloca).
- The reload is the routing's generic `ld.u32` (nv_thread_local_routing.cpp:345-346) or the trampoline's `*(uint32_t *)(uintptr_t)key` (default_trampoline.cu:284, 289).
- In PTX the store addresses through %SPL and the load through %SP = cvta.local(%SPL) at the same offset.
- eBPF bytecode level: only via a new by-value pseudo-helper plus constant tracking of stack slots. GUESS: the STL would stay while other helpers receive stack pointers. Not recommended.
- LLVM IR level: lower the constant-fd 1530/1531 lookups before optimization (F1), with the area as an IR parameter instead of the PTX-added one.
  - Store-to-load forwarding removes the reload and folds the bounds check when the key is constant.
  - GUESS (SROA): the [74 x i64] stack can disappear only if no stack address escapes. Pointers given to 503/504/505, or a remaining helper-1 key pointer, keep it.
  - Size estimate: 200-400 lines (overlay patch, request field, routing changes).
- PTX level (routing, small): when the key register's single definition is `add.s64 R, <%SP alias>, imm`, emit `ld.local.u32 k, [%SPL+imm]`.
  - Needs alias tracking of `add.u64 X,%SP,0` and `cvta.local.u64 %SP,%SPL`.
  - GUESS: ptxas forwards STL to LDL of the same address.
  - Forwarding the stored value itself needs reaching-store analysis, which is fragile.
  - Size estimate: 40-80 lines.

R4. A u64 accessed as two 32-bit generic loads or stores
- Mechanism (GUESS, consistent with evidence):
  - LLVM 15's IRBuilder takes the alignment from the module's DataLayout at creation time when none is given. /usr/lib/llvm-15/include/llvm/IR/IRBuilder.h:1676-1691: `if (!Align) { const DataLayout &DL = BB->getModule()->getDataLayout(); Align = DL.getABITypeAlign(Ty); }`.
  - The module has no DataLayout at that point (gen-compiler:220); it is set later (gen-ctx:1175).
  - Not verified: that LLVM 15's default layout gives i64 an ABI alignment of 4. The headers do not show the defaults.
- Evidence in routed.ptx (probe-function part, lines 1-7594):
  - LLVM's generic accesses are all 32-bit: 546 `ld/st.u32` lines.
  - Every one of the 40 generic 64-bit `ld/st.b64` lines is the routing's own atomic-guard code (%bpat). None comes from LLVM.
  - Stack slots are `ld/st.local.u64`.
  - The explicitly aligned atomic (compiler_utils.cpp:388) is a single `atom.add.u64`.
- Alignment facts:
  - The area is `.local .align 16` (routing .cpp:465), map offsets in it are 8-aligned (bpf_attach_ctx_cuda.cpp:556-562), and an entry sits at key*value_size.
  - 1531/1532 values are multiples of 8 (nv_gpu_model_maps.cpp:83) on cuMemAlloc bases.
  - Pointers from host-call lookups (default_trampoline.cu:340-348): alignment not stated anywhere I read.
- (a) Set the NVPTX DataLayout before IR generation in GPU mode: one line near gen-compiler:220, as an overlay patch. Every i64 access then claims 8-byte alignment.
  - PTX ISA 6.4.1 (ptx-isa.txt:3245-3248): "The address must be naturally aligned to a multiple of the access size. If an address is not properly aligned, the resulting behavior is undefined. … the instruction may fault."
  - Risk: packed data, 1530 maps with value_size % 8 != 0 (entry 1 and later), and CPU map values become undefined or fault the application's context.
- (b) Per site at IR level (needs F1): known 8-alignment (an `align` attribute or llvm.assume) on constant-fd 1530/1531/1532 lookups. LLVM then widens accesses at offsets that are multiples of 8.
- (c) A PTX peephole merging the 32-bit pairs: fragile.

R6. Inline the probe bodies into the kernel
- The PTX ISA has no inline/noinline directive: the performance-tuning directives are .maxnreg, .maxntid, .reqntid, .minnctapersm, .maxnctapersm, .noreturn, .pragma, .abi_preserve(_control), .minperctamemory (ISA 11.5, ptx-isa.txt:673-683). Observed: real CALLs remain at -O3. There is no documented way to make ptxas inline.
- A PTX-text inliner (in or after routing) must handle:
  - One body copy per exit site, some predicated or labeled (kretprobe :56-60). The predicate becomes `@!p bra skip`, and the label stays on the first instruction.
  - `ret` inside the body (the gate's `@%bpftime_off ret;` and LLVM's exit) must become `bra <end>`, or it would return from the kernel. This is how the gate survives, unless R9 hoists it.
  - Labels: ISA 9.7.14.4 (brx.idx) says branch targets "must refer to labels within the current function" (ptx-isa.txt:16185-16186). Label scope across nested `{}` blocks is not stated, so rename per copy.
  - Registers: the body declares `%rd<98>`, `%r<3>`, `%p<4>`, `%SP`, `%SPL` (routed.ptx). ISA 9.7.14.1 (ptx-isa.txt:16120-16122): "any variable declared within a scope is not available outside the scope". Shadowing an outer name is not stated, so rename per copy.
  - Depot: ISA 5.1.5 (c1-carry/docs/doc-quotes.txt:8): ".local state-space variables must be declared within function scope and are allocated on the stack". Whether ptxas overlaps the depots of several copies is not stated; worst case is +592 B of frame per copy.
  - Functions called from outside kernels (stub-replaced calls, kprobe_entry :58-81; memcapture) keep the .func.
  - Register pressure: patched mmq is 255 regs with 60 B spills, mmvq 56 regs (results/gpu/map-model-proto-20261116/ptx/ptxas_check-final.txt:3-4).
- Size estimate: 300-600 lines. High risk.

R7. Keep the thread-local map in registers
- (a) After R6: kernel `.reg .b64` words instead of the area.
  - In PTX text, every use of a direct-lookup result register must be a plain ld/st at a constant offset, rewritten into moves, including the 32-bit halves from R4.
  - Fall back to memory on any escape: r5 to a helper, a value pointer to a helper, a store or copy of the pointer, or atomics on it.
  - GUESS: ptxas will not register-promote a `.local` whose cvta.local generic address feeds generic loads.
- (b) Without inlining, words passed as call params and returned.
  - ISA 7.1.1 (ptx-isa.txt:3888-3890): "For targets sm_20 or higher, PTX restricts functions to a single return value, and a .param byte array should be used to return objects that do not fit into a register." So the return is one `.param .align 8 .b8 retval[8*W]`.
  - Calls can be predicated: ISA 9.7.14.5 example `@p call (d), h, (a, b);` (ptx-isa.txt:16266). Retval loads must then be predicated too.
  - Inside the probe it helps only if done at IR level: lookups become GEPs into an alloca initialized from the args, and the words are returned at exit. GUESS: SROA promotes it only with constant keys and no escapes. A PTX-level function-local copy just moves the memory.
  - Routing changes: call-site rewrite (:431-453), prologue (:464-471), probe signature (:513-533).
- What breaks or forces the fallback:
  - non-constant fds (they get r5);
  - helpers 2/3 on 1530 (default_trampoline.cu:351-366);
  - dynamic keys;
  - atomics on 1530 values: pt_tlatomic.bpf.c:23-26 has a fetch-add with result, a u32 add on half a u64, and an exchange;
  - value addresses passed to helpers;
  - areas larger than a few words (register pressure, mmq at 255).
  - pt_lat (one u64, key 0, plain access) and pt_carry (two u64, plain; tools/pt_carry.bpf.c:61-84) fit.
- Size estimate: large (IR overlay, plumbing, routing).

R9. Hoist the gate to kernel start

R10. Warp combine of sum-map adds

- redux.sync is .u32/.s32 only and needs sm_80 (ISA 9.7.15.13, ptx-isa.txt:17559-17595). A non-constant 64-bit operand needs shuffles.

  - :447 says a mask known by construction "is not valid in exit probes or in `__memcapture`".

- Where:

DOCUMENT CLAIMS, SEPARATED (PTX ISA 9.5 unless noted)
(a) Guaranteed by the text
- match.sync waits for "all non-exited threads from membermask" with "the same qualifiers and same membermask value" (9.7.15.11, ptx-isa.txt:17511-17513); it requires sm_70.
- sm_20+ functions have a single return value, with a .param byte array for larger objects (7.1.1, :3888-3890).
- A variable declared in a `{}` scope is not available outside it (9.7.14.1, :16120-16122).
- `.local` must be declared within function scope under the ABI (5.1.5, doc-quotes.txt:8).
- clz.b64 exists (9.7.1.16). %globaltimer is a 64-bit ns timer "intended for use by NVIDIA tools" (10.28).
(b) Explicitly undefined by the text
- match.sync when "the executing thread is not in the membermask" (9.7.15.11).
- Scalar atom through a generic address that does not point to .global/.shared (9.7.15.5, ":16801-16803", stated as a restriction).
- Misaligned access (6.4.1, :3245-3248).
- %globaltimer value when JIT-compiled to other targets (10.28).
(c) Not mentioned in the texts read
- That activemask results agree across the lanes they name (c5 README:409-430: searched, "Not found").
- Label scope across nested `{}` blocks.
- Whether an inner block may shadow an outer register name.
- Whether ptxas inlines .func calls, or how to request it.
- Whether ptxas overlaps several `.local` depots.
- Whether ptxas may move an inlined %globaltimer read across memory ops.
- Alignment of host-call map-lookup results (bpftime code).
