## Other findings

- PATCH BUG (most important): the 'unseen' latch fires falsely on launches the hooks do note. 13 of 256 non-graph A-family runs have unseen_hits=1: r1 c02_AB, r1 c11_AB, r2 c11_AC, r2 c03_AB, r2 c06_AB, r2 c08_A, r2 c08_ABC, r2 c12_ABC, r2 c16_A, r2 c17_ABC, r4 c05_A, r4 c07_AB, r4 c10_A. unseen_hits is never reset, the threshold is 2 and the latch is permanent. In a longer-lived process, a second false hit would silently turn A/AC into M100-like behaviour with no parking (c11 CPU would go from 0.002 to ~0.011). Likely cause: note() runs after original() returns (a post-launch hook; the first note also calls cuEventCreate), and wait_for_note wakes only on notes, not on flag1. So a short probed kernel (the warm-up spins 1 us) can post its host call before its own note, and a backstop that expires in that gap counts as a hit. In c11/c02 the hit left no visible long latency, consistent with it being the warm-up record, which summarize drops. Fix: decay the counter or require consecutive hits. Test: a 10x longer c02, or many short probed kernels, while watching unseen_latch.
- Attribution gap for C: the adaptive window is barely exercised. win0 is 100% of requests in every single-lane cell except c14 (82%) and c15 (99%); cap_forced = 0 everywhere; win300 is about 0 (2 events in c14 ABC). Every AC win in single-lane cells is 'no 200 us busy poll + 8 x 20 us deferral sleeps'. A control is missing: A with HOT_US=0 (and/or AC with K_DEFER=0). Without it the gain cannot be credited to C's grow/shrink logic.
- Set definitions do not match the code for ABC. In the C hot path with B on, a closed gate gives sleep_us(P_MIN=10), not cpu_relax. So ABC vs AC is not 'AC plus WFE' in burst cells (c05: hot_iters 77k vs 4.0M, CPU 0.045 vs 0.114, cost per call 21.6 vs 17.1 us). Also ABC keeps C's deferral sleeps when the gate is open, which is why ABC CPU is about 0.93 vs AB about 1.0.
- B has a cost under load even with the gate closed. AB vs A > 1 ms is 1.25-1.75% vs 0-0.5% in c10 and 4.0-4.4% vs 3.6-3.8% in c01, in every round (ABC vs AC in c10: 2.25 vs 1.69%). The only difference is gate_check's two preads every 1 ms. The latch counter mixes run_delay trips and late-WFE trips, which cannot be separated. WFE returns about every 100 us (wfe_waits about 27 per request in c02/c18, ~10.7k/s, i.e. the arm64 event stream), so LATE_WFE_US=500 fires only on preemption longer than 500 us. Also, loadavg's 4th field is an instantaneous count, and the open/close thresholds (>=5 closed, <=4 open) leave no hysteresis band; only OPEN_STREAK=3 damps it, so it flaps (c16: ~1,000 opens, 89 latch trips per run).
- The rotation is only partly balanced. rounds.sh uses offsets r=1..4 out of 7, so each set gets only 4 of the 7 positions. P sits only in positions 3-6, always right after ABC (and right before W in r2-r4). AC sits only in 0-3; M100 in 0, 1, 5, 6; P/AB/ABC never run first. Each cell's first run follows the previous cell's last set (a different workload). With locked clocks and temps at or below 54 C the effect is probably small, but there are signs. c06 M100 per-launch is about 2,900 in r1/r2 (early positions) and about 2,877 in r3/r4 (late), the same order as some of the small claimed deltas. Use all 7 rotations, or randomise, before relying on deltas under ~1%.
- Build fairness. diff -rq of the W worktree (46f5a7cb, clean) against policy/src over runtime/ and attach/ shows only bpf_attach_ctx_cuda.cpp differs, so the comparison is fair. Caveats: W's libbpftime-agent.so was built at 16:10, 12 minutes before commit 46f5a7cb (16:22), so the binary-to-commit match is assumed, not shown. And W never sets PR_SET_TIMERSLACK (default 50 us) while M100 and the A-family use 1 us. That matters where W sleeps (c18's 533 us, the c09/c10 gaps).
- Statistics. Latency percentiles pool all runs and processes, so p99/max can come from a single run: c18 ABC r2 CPU 0.562 vs ~0.94 in other rounds; c13 ABC r3 p99 2,397 vs ~373 in other rounds; c16 W r4 p99 2,369. For bimodal tails (c13/c16) the > 1 ms share is the stable statistic and p99 is not. Report per-round ranges, or medians of per-run percentiles. Small-count cells (c10: 400 calls per run; c11: 1 call per run) need event counts, not percentages.
- c17 baseline problem. P's per-launch (3,602-3,661) is above W's (3,072-3,298) in every round, so P is not a no-overhead floor there. The victim's main thread (device_flags 0x8, P CPU 0.011, so it blocks in sync) suffers the same wake-up delay, and per-launch or 'load vs P' comparisons in c17 are confounded by it.
- The CLAIMS table never notes that idle parking happens mostly at start-up. parks ~296 / park_timeouts ~293 appear in every no-gap no-load cell, and the matching CPU and power are partly start-up (~300 ms before the first launch, outside the timed window for CPU but inside the process). The us_* counters are integer-microsecond sums per ~100 ns iteration, so they undercount by up to ~2x; flag this before anyone uses them.
- Minor harness asymmetries: (a) non-P sets have the loader (syscall-server) process resident during the run, and P has none, which slightly affects load rate and power; (b) for loaded cells the load starts 1 s before the loader attach wait, so non-P victims start later into the load; (c) in c18 summarize keeps the graph warm-up latency record; (d) c14 power medians mix 1-4 runs per set.
