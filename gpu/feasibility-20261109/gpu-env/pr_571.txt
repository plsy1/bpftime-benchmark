One real conflict, in `prefill_patched_kernel_functions_from_loaded_fatbins`: upstream had refactored it to resolve entry points per fatbin record via `collect_ptx_entry_functions(rec->original_ptx)` with a `collect_all_kernels_to_patch()` fallback, while this branch had added basic-block name handling. Resolved by keeping upstream's structure and layering the BB handling on top.

## Fix 1 — PTX ISA version normalization (`fd95778`)

**Reported problem:** `directly_run_on_gpu` reached the direct nvPTXCompiler path without the version downgrade/retry used elsewhere, so PTX declaring `.version 9.2` was rejected by a compiler supporting up to 8.5.

The version-handling logic was extracted into a new header-only `attach/nv_attach_impl/ptx_version_utils.hpp` (`bpftime::attach::ptx_version`) exposing `locate`, `rewrite`, `clamp_to`, and `supported_version_from_error_log`. Header-only is required here because `nv_attach_impl_ptx_compiler` is a shared library loaded through `dlopen` and does not link against `bpftime_nv_attach_impl`, so the two cannot share a compiled symbol.

Both compile paths now clamp `.version` up-front against the compiler's reported capability, and on failure parse the supported version out of the error log (`current version is '8.5'`) and retry once. Also fixed an nvPTXCompiler handle leak on the error paths — `nvPTXCompilerDestroy` was missing.

**Verified** by reproducing the exact failure locally with `ptxas -c -arch=sm_75` (local ptxas caps at PTX ISA 8.0): `ptxas fatal: Unsupported .version 9.2; current version is '8.0'` before, clean assembly after.

## Fix 2 — trampoline symbol hygiene (`fd95778`)

**Reported problem:** `cuda-counter` built a trampoline from nvcc-generated PTX, which then collided on duplicate `$str` symbols with the application PTX.

The trampoline PTX is concatenated ahead of the application PTX before being handed to `ptxas`, so nvcc's generic string-literal symbols (`$str`, `$str$1`, …) collide. Generation now rewrites them to `$__bpftime_tramp_str*` and strips `.file`/`.loc` debug directives.

One subtlety: the strip pattern must be anchored, because `.loc` also matches `.local` — the PTX depot declarations — and stripping those corrupts the output.

**Verified** by reproducing the collision (`error: Duplicate definition of variable '$str'` / `Inconsistent redefinition of variable '$str'`) and confirming it assembles cleanly afterwards.

## Fix 3 — dead code removal (`3677ce6`)

A cleanup pass over the whole `upstream/master..dev` diff: **-602 / +352 lines**. Two of these were latent bugs rather than clutter.

- **`default_trampoline.cu`** — removed the `__bpftime_helper_keepalive` global and twelve `bpftime_keep_args5` inline-asm barriers. Compared nvcc output with and without them: identical exported symbols (19 helpers) and identical helper parameter signatures; the barriers only emitted dead `ld.param` instructions. Unused parameters are unnamed again. This shrank the file's diff against upstream from 107 lines to 30.
- **`nv_attach_impl.cpp`** *(bug)* — `derive_bb_tracepoint_entry` was unreachable and also incorrect: it resolved a `.func`, which `cuModuleGetFunction` can never return. Removing it also fixed the `CUfunction`→name cache being populated with the attach-spec string instead of the real module symbol.
- **`nv_attach_impl_frida_setup.cpp`** *(bug)* — the single-patched-kernel fallback in `cu_launch_kernel_common` ran unconditionally, overwriting an already-resolved `CUfunction` and recording the launch twice. Now only used when the name-based lookup fails.
- **`ptxpass_bb_tracepoint/main.cpp`** — `BBKprobeParams` was advertised through `cfg.parameters` but never deserialized or read; two label-position variables were only ever written.
- **`ptx_compiler.cpp` / `trampoline/Makefile`** — unused includes, and leftover `CLANG`/`LLC`/`CLANG_FLAGS`/`CUDA_LIBS` from before PTX generation moved to nvcc.

`trampoline_ptx.h` was regenerated (it still contained keepalive artifacts). It now declares `.version 8.0` rather than `9.2`, which is more portable — and the runtime normalizes it regardless.
