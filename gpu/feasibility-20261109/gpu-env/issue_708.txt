#708 [BUG] bpftime GPU attach: unattached kernel's `__device__` global address splits between mirror and launch [OPEN] by emmajiafan created 2026-10-20T02:42:06Z updated 2026-10-20T02:42:06Z closed None
LABELS: ['bug']
BODY:
**Describe the bug**

In the GPU scenario, the bpftime agent (injected via LD_PRELOAD) breaks the **consistency of a `__device__` global between an unattached kernel and the host** — the kernel writes one patched module's copy while the host reads/writes a different patched module's copy.

In the `cuda-counter/vec_add` example there is a business kernel `test_kernel_2` that does `counter++` on `__device__ int counter`; `vectorAdd` reads `__constant__ int d_N`. `cuda_probe.bpf.c` attaches only `vectorAdd`, not `test_kernel_2`. Running under the agent:

- `test_kernel_2`'s `counter++` lands on the `counter` copy of the **second patched module (with kprobe+kretprobe)**;
- but the host reads `counter` back via `cudaMemcpyFromSymbol`, whose mirror locks onto the **first patched module (kprobe only)**, whose `counter` stays at the initial value 233, so the business prints `counter = 233 (expected …)`;
- likewise `vectorAdd` reads `d_N` in the second module while `cudaMemcpyToSymbol` writes the first module's `d_N` via mirror (stuck at 0), printing `C[1]=0` (should be 3).

Running bare (no agent), `counter == expected` and `C[1] == 3` hold exactly, proving the problem is in the bpftime attach layer, not the workload.

**Root cause**: the `kprobe` + `kretprobe` pair on `vectorAdd` is attached in two separate calls, making the late-attach bootstrap run twice and load two patched module sets. Variable mirroring and kernel redirection then lock onto different module sets, splitting the device address of the `__device__`/`__constant__` globals between them:

1. `create_attach_with_ebpf_callback` attaches once per SEC. The first attach (`kprobe`) triggers bootstrap and loads a module set with only kprobe instrumentation (A). The second attach (`kretprobe`) sees `late_bootstrap_done == true`, takes the "new hook added after bootstrap" branch, calls `reset_late_bootstrap_state_for_next_attach()` and re-runs bootstrap, loading a kprobe+kretprobe module set (B).
2. But `reset_late_bootstrap_state_for_next_attach()` only resets the `once_flag` and the `done` flag — it does not drop module A. `bootstrap_existing_fatbins()` always `emplace_back`s new fatbin records, so two CUmodule sets accumulate.
3. The two index directions pick different sets:
   - **launch redirection**: `prefill_patched_kernel_functions_from_loaded_fatbins` iterates all records and `record_patched_kernel_function` overwrites by symbol name, ending up at the **last set (B)**;
   - **variable mirroring**: `mirror_cuda_memcpy_to_symbol` / `mirror_cuda_memcpy_from_symbol` iterate records and `cuModuleGetGlobal` **breaks and caches on the first hit**, ending up at the **first set (A)**.
4. The result is "kernel writes B, host reads/writes A" — a device-address split.

**Fix**: in `create_attach_with_ebpf_callback`'s "new hook added after bootstrap" branch, call `clear_patched_state_for_next_session()` (drop module A and its symbol/kernel/global caches) before re-running bootstrap, so the two attaches end up with a single module set. Verified remotely.

**To Reproduce**

Environment: NVIDIA L4 GPU, CUDA 12.8, bpftime build tree `/opt/bpftime/build-llvm16`.

1. Build the example:
   `make -C /opt/bpftime/example/gpu/cuda-counter`
2. Start the server (kprobe+kretprobe skeleton):
   `cd /opt/bpftime && export BPFTIME_SOURCE=/opt/bpftime && BPFTIME_LOG_OUTPUT=console LD_PRELOAD=build-llvm16/runtime/syscall-server/libbpftime-syscall-server.so example/gpu/cuda-counter/cuda_probe > srv.log 2>&1 &`
3. Run the workload under the agent (infinite loop terminated by timeout):
   `cd /opt/bpftime && timeout 40 env BPFTIME_LOG_OUTPUT=console LD_PRELOAD=build-llvm16/runtime/agent/libbpftime-agent.so example/gpu/cuda-counter/vec_add > victim.log 2>&1`
4. Inspect the self-reported round counter and C values in `victim.log`:
   `grep -E 'counter = |C\[1\]' victim.log`
5. For comparison, run the same `vec_add` without the agent and inspect the same lines.

(Note: `counter`'s initial value 233 comes from `int i = 233; cudaMemcpyToSymbol(counter, &i, sizeof(i));`; `d_N` comes from `int h_N = 1 << 20; cudaMemcpyToSymbol(d_N, &h_N, sizeof(h_N));` in `vec_add.cu`.)

**Expected behavior**

`test_kernel_2` increments `counter` every round, so the host read should grow and equal `expected`; `vectorAdd` should read `d_N` such that `C[1]=3`:

```
counter = 234 (expected 234)
counter = 235 (expected 235)
...
C[0] = 0 (expected 0)
C[1] = 3 (expected 3)
```

Attaching should only observe `vectorAdd` and must not change the semantics of `test_kernel_2`, nor corrupt the host↔device consistency of the `__constant__` variable read by `vectorAdd`.

**Additional context**

- **History of root-cause revisions** — three conclusions:
  1. First attributed to "the `st.global [counter]` write being lost in the ptxas/cubin relocation layer" (the old title of this file) — **not true**: the write lands in the right module set (B), it just isn't the one the host reads (A).
  2. Then attributed to "`read_function_symbols` only collecting `STT_FUNC` (missing `STT_OBJECT`) / mirror not demangling" — that is the other half of the same-scenario `C[1]=0` issue (PR #695's scope), **not** the root cause of the stuck-at-233 counter.
  3. Final: "kprobe+kretprobe double attach → two bootstrap rounds → two patched module sets → mirror picks A while launch picks B" — consistent with the two-round bootstrap logs and the write-B/read-A behavior, verified fixed remotely.
- Decisive log evidence: two distinct patch hashes `fe8eb93b…` (A) vs `5601047d…` (B), `ingested 3 fatbin(s) ×2` (two rounds), `mirror to_symbol ptr=…a008/a900` locking A, `launch -> PATCHED` redirecting to B.
- Why `threadscheduling`  is unaffected: its `threadscheduling.bpf.c` has only a single `kprobe` SEC with no matching `kretprobe` — one attach = one bootstrap = one module set, no split.
